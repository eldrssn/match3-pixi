# Modal System

## Назначение

Модальная система даёт единый способ открывать cross-route UI поверх текущего
экрана. Она состоит из двух уровней:

- `src/shared/modals` - generic-механика: `Modal` (portal, layout, z-index,
  анимации через `motion/react`, focus trap) и `ModalsHost` (DOM-контейнер
  слоя, отложенный размонтаж под exit-анимацию, `inert` для фона). О конкретных
  модалках приложения этот слой ничего не знает;
- `src/widgets/modals` - прикладной слой проекта: ключи модалок, типы props,
  Zustand store, арбитраж видимого слоя, реестр вью (`ui/modalViews.tsx`),
  загрузчики чанков (`ui/modalChunks.ts`) и сам `ModalsProvider`.

## Runtime Flow

1. `App` монтирует `ModalsProvider` (из `@/widgets/modals`) внутри каркаса
   приложения и внутри `BrowserRouter`, поэтому modal views видят Router-контекст и могут
   использовать `useNavigate`.
2. `ModalsProvider` связывает store и реестр вью с `ModalsHost`.
3. `ModalsHost` создаёт `<div id="modals">` **в `body`** (не внутри
   React-дерева приложения) и раздаёт его через контекст.
4. Feature/widget код открывает модалку через `useShowModal()` (или
   `useModalsStore.getState().show(...)` вне React, как хост партии):
   `showModal(MODAL_KEYS.VICTORY, { onPlay, onHome })`.
5. Store сохраняет key + typed props в `modals` и порядок открытия в `openKeys`.
6. `useActiveLayer()` (поверх чистой `resolveActiveLayer`) выбирает реальные
   `visibleKeys`.
7. `ModalsHost` lazy-loads modal view из `modalViews.tsx`.
8. View рендерит shared `<Modal />`, который через portal попадает в `#modals`.

Почему контейнер слоя лежит в `body`:

- фон (`#root`) можно пометить `inert` целиком, не задев сам слой модалок;
- слой не наследует `overflow`/`padding` каркаса и колонки контента и
  покрывает всё окно (`position: fixed`): затемнение ложится на весь
  однотонный фон, а не только на колонку, иначе на десктопе по бокам
  оставались бы светлые полосы. Карточка задана через `option` и по ширине
  совпадает с колонкой.

## Layers And Stacking

Ключи объявлены в `src/widgets/modals/model/modal-registry.ts`.

- `base` - самостоятельная модалка. Если открыто несколько `base`, видна одна:
  сначала выигрывает меньший `priority`, при равном приоритете - открытая
  последней.
- `stacked` - модалка поверх текущей. Используется для подтверждений, ошибок,
  успешных действий и других overlays, которые не должны скрывать контекстную
  base-модалку.

Приоритеты осмысленные, а не одинаковые: `1` - явное действие пользователя
или системная ошибка, `2` - карточки геймфлоу. Сейчас в реестре near-miss
`outOfMoves` (`1`: исхода ещё нет, она важнее результата), карточка уровня
`levelStart` и результаты `victory`/`defeat` (все `2`).

`closeOnRouteChange: true` в записи реестра означает, что модалка закрывается
при смене маршрута (`useCloseModalsOnRouteChange`): геймфлоу и меню привязаны к
экрану, с которого открыты, и не должны «переезжать» в другой раздел.

Слои:

- `global` - обычный product UI;
- `system` - ошибки и технические блокеры (сейчас пустой).

## How To Add A Modal

1. Добавь ключ в `MODAL_KEYS` и запись в `MODAL_REGISTRY` (приоритет, слой,
   stacking, при необходимости `closeOnRouteChange`).
2. Добавь props в `TModalPropsMap`.
3. Создай компонент в `src/widgets/modals/ui/<name>/ui`, данные - в
   `src/widgets/modals/ui/<name>/model`.
4. Экспортируй компонент через локальный `index.ts`.
5. Добавь загрузчик чанка в `src/widgets/modals/ui/modalChunks.ts` и вью в
   `src/widgets/modals/ui/modalViews.tsx`. Оба реестра - `Record<TModalKey, …>`:
   пока для нового ключа нет загрузчика и вью, проект не скомпилируется, и
   модалка не сможет молча отрисоваться пустотой.
6. Открывай модалку из feature/widget кода через `useShowModal()`.

Отдельных `showModalX`/`hideModalX` экшенов и селекторов на каждую модалку
больше нет - store параметризуется ключом:

```tsx
const showModal = useShowModal();
const hideModal = useHideModal();
const isOpened = useIsModalShowed(MODAL_KEYS.VICTORY);

showModal(MODAL_KEYS.VICTORY, {
  onPlay: () => startNextParty(),
  onHome: () => goHome(),
});
```

`useHideModals()` закрывает несколько модалок одним обновлением стора - нужно,
когда нижняя модалка не должна мелькнуть между двумя `hide()` (см.
`useCloseModalsOnRouteChange`; хост партии зовёт тот же `hideMany`).

## Modal Primitive

`Modal` принимает:

- `isOpened`;
- `onClose`;
- `fullscreen`;
- `backdrop`: `default | transparent | solid | dim`;
- `backdropBlur`;
- `surface`: `light | dark` - оформление карточки. `dark` даёт тёмную карту с
  нейтральной обводкой по дизайну игровых модалок; раньше каждая модалка
  перебивала белый фон примитива собственным классом с искусственно поднятой
  специфичностью (`&.card`);
- `contentOverflow`: `hidden | visible`;
- `closeOnEscape`;
- `closeOnOverlayClick` - клик мимо карточки закрывает модалку. Включено по
  умолчанию для всех модалок; выключать только там, где выбор обязателен.
  Обработчик висит и на `overlay`, и на слое `wrap`: `wrap` растянут поверх
  оверлея на весь слой, поэтому клик до оверлея просто не доходил и закрытие по
  фону не работало ни в одной модалке. Сама карточка гасит всплытие, так что
  клики внутри неё модалку не закрывают;
- `titleId` / `descriptionId` - опциональные id для `aria-labelledby` /
  `aria-describedby` диалога; конкретная модалка генерирует их через `useId()`
  и вешает на свои `title`/`description` элементы (см. `ModalDefeat`).
- `animateHeight` - анимировать изменение высоты карточки (см. ниже). Включено
  по умолчанию для всех не-fullscreen модалок; выключать явно
  (`animateHeight={false}`) стоит только там, где нет смысла даже держать
  наблюдатель - высота карточки заведомо неизменна на всё время её жизни.
- `showCloseButton` - крестик в правом верхнем углу карточки (`shared/modals`
  рисует его сам, зная только `onClose` и `surface` - никакой продуктовой
  логики). Выставлять только модалкам, у которых среди действий нет отдельной
  кнопки чистого закрытия. Сейчас его не выставляет ни одна: у
  `victory`/`defeat` выбор одного из двух действий обязателен, клик мимо
  карточки выключен (`closeOnOverlayClick={false}`), а Escape ведёт туда же,
  куда «На главную».

Обычная модалка получает centered card, fullscreen-модалка занимает весь
слой - всё окно высотой `--app-viewport-height`. Overlay и card
анимируются через `motion/react`. Изменение высоты карточки анимируется по
умолчанию (`animateHeight`, `useAnimatedContentHeight` в `shared/modals/lib`):
`.content` следит за собой через `ResizeObserver` (между переходами у него нет
инлайн-`height`, поэтому замер отражает настоящий естественный размер), и при
живой смене контента (например, спиннер -> содержимое) сначала
замирает на старой высоте тем же тактом, а затем императивно доезжает до новой
через `useAnimate` - `motionDuration.medium` / `motionEase.enter`, те же токены,
что и у появления самой модалки. Специально не `layout` motion (FLIP через
`scale`): тот меряет карточку на каждом коммите и анимирует её бокс
трансформом, из-за чего содержимое на время перехода заметно искажается вместе
с ней. На время самого перехода `overflow` карточки принудительно `hidden`,
даже при `contentOverflow="visible"` (`victory`) - иначе растущий контент был
бы виден раньше, чем до него дорастёт бокс. Кадры `ResizeObserver`, пришедшие
во время самого перехода, гасятся (иначе каждый промежуточный px запускал бы
новый цикл заморозки), но не теряются: по завершении узел перемеряется уже на
`height: auto`, и если контент за это время изменился ещё раз, переход
доводится до актуальной высоты. Без этой доводки второй переход подряд стартовал бы от устаревшего значения и
давал скачок. Выключать проп
(`animateHeight={false}`) стоит только там, где высота карточки заведомо
неизменна на всё время её жизни - смысла даже держать наблюдатель нет. На
fullscreen-экране проп игнорируется - высоту задаёт вьюпорт. Каждое
смонтированное окно получает свой
z-index через `useModalStackZIndex`, а body scroll блокируется через
reference-counted `useBodyScrollLock`, поэтому несколько одновременно
смонтированных модалок (base + stacked) не мешают друг другу при разном порядке
закрытия.

Доступность:

- диалог - узел `.dialog` вокруг `.wrap` с карточкой: на нём `role="dialog"`,
  `aria-modal="true"`, `aria-labelledby`/`aria-describedby` и ловушка фокуса;
- фокус уходит внутрь диалога, Tab/Shift+Tab ходят по кругу внутри него, при
  закрытии фокус возвращается на элемент-триггер (`useFocusTrap`). Слушатель
  висит на самом контейнере, поэтому при стеке модалок Tab обрабатывает только
  та, внутри которой фокус;
- Escape закрывает **только верхнюю** модалку: слушатель один на приложение, а
  порядок ведёт `useModalEscapeStack`. Обработчик на каждой
  `ModalLayout` закрывал бы одним нажатием весь стек;
- пока хотя бы одна модалка **в DOM**, `#root` помечен `inert` + `aria-hidden`,
  поэтому фон недоступен ни с клавиатуры, ни скринридеру, ни указателю. Признак
  здесь - смонтированные модалки, а не показанные: после `hide()` карточка
  доигрывает exit-анимацию и всё это время закрывает экран, а снятый раньше
  `inert` пропускал тап в то, что лежит под ней. Тот же довод, что у паузы
  рантайма на модалке результата;
- внутри модалки нельзя использовать `main`/`h1` - под ней остаётся страница со
  своими landmark-ами.

При `hide()` store переводит модалку в `isOpen: false`, но не стирает её
`props` - они остаются доступны, пока не доиграет exit-анимация. Реальная
очистка происходит через `purge()`, который `ModalsProvider` вызывает из
`useMountedModalKeys` только когда модалка действительно покинула DOM. Это
не даёт контенту "мигнуть" дефолтными props во время закрытия.

Отсюда же берётся `useIsModalMounted(key)`: запись есть в сторе ровно до
`purge`, поэтому наличие ключа - это "модалка ещё в DOM", включая хвост
exit-анимации. Это единственный способ снаружи дождаться полного ухода
модалки, не зная про таймеры хоста; так главная держит новую партию на паузе,
пока уходит карточка результата (`useHasMountedModals`, см.
[docs/game-flow.md](./game-flow.md)).
Если хост размонтируется раньше, чем доиграют exit-анимации, отложенные
`onUnmounted` не теряются - `useMountedModalKeys` выполняет их в своём
cleanup, иначе в сторе остались бы записи о модалках, которых уже нет.

## Prefetch

Чанки модалок партии (`victory`/`defeat`/`outOfMoves`) подтягивает хост
партии (`pages/main/model/useMainFlowStore`) через `prefetchModalChunk()` на
старте партии, чанк карточки уровня (`levelStart`) - главная на маунте: «Играть»
открывает её первым же тапом. Idle-прогрева чанков на старте приложения нет.

## Boundaries

- `shared/modals` не импортирует `widgets`/доменные модули и не знает о
  конкретных продуктовых сценариях: реестр вью приходит в `ModalsHost` пропом
  `renderModal`.
- `widgets/modals/model` владеет key/props/store, но не выполняет API-запросы.
- Внутри виджета модалки импортируют друг друга относительными путями, снаружи -
  только через публичный `@/widgets/modals`.
- Кнопки тёмных модалок - общий `shared/ui/modalButton`.
- Не открывай глобальные модалки локальным `useState`, если их могут вызвать
  разные routes или runtime события.

## Validation

После добавления новой модалки проверь:

- `npm run type-check`;
- `npm run lint`;
- `npm test`;
- `git diff --check`.

Если модалка видима пользователю в текущем сценарии, проверь её в браузере на
mobile viewport и убедись, что текст не вылезает из card/buttons.
