# Game Flow

Рантайм партии - Pixi v8 (WebGPU с откатом на WebGL), твины - GSAP 3 на часах
рантайма, вид клетки Spine - ленивый чанк. Это порт Phaser-шаблона; как
переносилось и чем отличается - журнал [PLAN.md](./PLAN.md).

Описывает геймфлоу «кнопка Играть → экран партии → победа/поражение → карточка
результата». Сама партия - Match-3 виджет `widgets/game` (`GameScreenLazy`):
уровень и бустеры он получает пропсами, а исход, запрос выхода и отказ
рантайма отдаёт колбэками (`IGameScreenProps` в
`widgets/game/model/gameScreenTypes.ts`). Про уровни, экраны, модалки и
прогресс виджет ничего не знает - это зона хоста. Хост в шаблоне один -
главная `/` (`pages/main`), сценарий целиком живёт в
`pages/main/model/useMainFlowStore.ts`.

Кнопки исхода («Выиграть»/«Проиграть») и «Фраза» на экране партии - отладка:
они рендерятся **только под `?gameDebug=true`** (`readQueryGameDebug` в
`shared/lib/routing`, хост передаёт его виджету пропом `debug`). Безусловные
кнопки означали бы, что любой игрок выигрывает уровень, не сыграв. Флаг именно
query, а не `import.meta.env.DEV`: кнопки нужны QA на обычном стенде с
production-бандлом. Кнопки выхода среди них нет - выход идёт из канваса. Там
же видно зерно партии (`seed N`): его переносят в `?seed=N`, чтобы повторить
раскладку добора и перемешки (см. [Движок доски](#движок-доски)).

Экран партии - **не модалка** и не маршрут, а режим главной `/`: во время
партии контент главной не рендерится, а игра занимает всю страницу. Модалки
геймфлоу - карточка уровня перед партией (`levelStart`), near-miss «Ещё
чуть-чуть!» (`outOfMoves`) и результаты партии (`victory`/`defeat`).

## Схема

```
Главная `/`: «Играть · уровень N», «Уровни», «Витрина», «Редактор» (pages/main/ui/MainActions)
        │  pointerdown «Играть» → prefetchGameScreenChunk()
        │  click «Играть» → play()   уровень: `?level=N` (в границах каталога) или открытый
        │  click «Уровни» → openMap() → карта (pages/main/ui/LevelMap), тап по уровню
        │  click «Витрина» → openShowcase() → список (pages/main/ui/ShowcaseList),
        │      тап → playShowcase(key) → startParty({ kind: 'showcase', key }) без карточки
        ▼
openLevelStart(levelNumber)      карточка levelStart: цели, ходы, лучшие звёзды,
        │                        предуровневые бустеры (не на первом уровне)
        │  уровня нет в каталоге → screen: home, failure: 'board'
        │  «Играть» на карточке → onStart(preBoosters)
        ▼
startParty({ kind: 'pack', levelNumber }, preBoosters)  screen → game, partyId + 1,
        │  party: { source, level, title?, boosters, preBoosters, tutorial }
        │  warmGameAssets() + warmPartyAssets() + prefetch чанков модалок партии
        ▼
<GameScreenLazy key={partyId} {...party} paused debug quality
                onFinish onOutOfMoves onTutorialSeen onExitRequest onError />
        │  boosters: [] на первом уровне (resolvePartyBoosters), иначе DEFAULT_LEVEL_BOOSTERS
        │  tutorial: механики уровня, которых игрок не видел → подсказки перед ходом
        ▼
ходы кончились, цели нет → onOutOfMoves(offer)
        ├─ первый раз за партию → карточка outOfMoves: «+5 ходов» → offer.continueWith(5)
        └─ «Сдаться» / повторно   → offer.giveUp() → поражение
        ▼
GameStore: isGameEnded && isFinaleFinished (или debug-кнопка)
        │  победа: финальный бонус (ходы → ракеты) до концовки
        │  useGameRuntimeEvents → onFinish({ isVictory, score, stars })  (один раз на маунт)
        ▼
finish(outcome)                  screen: game → result
        ├─ прогресс: победа открывает следующий уровень, звёзды и очки - рекорды
        │  (только партия пака; витрина прогресс не пишет)
        └─ showModal(VICTORY | DEFEAT, { onPlay, onHome, score, stars })
        ▼
victory: звёзды и очки; «Дальше» (карточка следующего уровня) / «На главную»
defeat:  «Ещё раз» (карточка того же уровня)                  / «На главную»
витрина: «Дальше» - следующий уровень витрины, «Ещё раз» - тот же, сразу партией

pointerup кнопки выхода в канвасе → GameStore.exitButtonOnClick()
        │  isExitRequested → useGameRuntimeEvents → onExitRequest()
        └─ хост: goHome()      screen: → home, подтверждения нет

GameStore.failRuntime(reason) → onError(reason)
        └─ хост: fail(reason)  screen: → home, главная показывает причину
```

## Хост партии: `useMainFlowStore`

| `screen`   | что на экране                                                                     |
| ---------- | --------------------------------------------------------------------------------- |
| `home`     | заголовок, «Играть · уровень N»/«Уровни»/«Витрина»/«Редактор», причина отказа     |
| `map`      | карта уровней на фоне главной: звёзды, текущий, закрытые; тап - карточка          |
| `showcase` | витрина: блокеры, спецфишки, комбинации списком; тап - сразу партия               |
| `game`     | `GameScreenLazy` с `key={partyId}` и пропсами из `party`                          |
| `result`   | доски нет (рантайм уничтожен по исходу), фон партии и карточка `victory`/`defeat` |

- Текущий уровень («Играть · уровень N», подсветка на карте) - не поле
  стора, а селектор `selectCurrentLevel`: самый дальний открытый уровень
  прогресса в границах каталога (`resolveCurrentLevel`). Переигровка старого
  уровня с карты его не сдвигает; откуда идущая партия - `party.source`.
- `progress` - прогресс игрока (`features/match3Host/model/levelProgress`): открытый
  уровень, лучшие звёзды и очки, знакомые механики. Живёт в `localStorage`,
  стор держит копию в памяти и пишет её на победе (`applyPartyResult`), на
  прочитанной подсказке (`tutorialSeen`) и на сбросе (`resetProgress`).
- `partyId` - `key` экрана партии, новый на каждый старт. Смена ключа и есть
  перезапуск рантайма: отдельного «рестарта» у виджета нет.
- `party` - `{ source, level, title?, boosters, preBoosters, tutorial }`
  текущей партии: источник (`{ kind: 'pack', levelNumber }` - номер в каталоге,
  его исход пишется в прогресс; `{ kind: 'showcase', key }` - уровень витрины,
  вне прогресса) и ровно то, что уходит пропсами виджету. Партия витрины
  получает `DEFAULT_LEVEL_BOOSTERS`, подсказки всех механик уровня
  (`listLevelMechanics`, даже знакомых) и подпись `Витрина · <механика>`
  (проп `title`; без него виджет пишет «Уровень N» по `level.id`). Его собирает `startParty`, вне
  `screen: 'game'` - `null`. Страница уровень и бустеры сама не вычисляет.
- `continuesUsed` - сколько раз партия взяла добавочные ходы: near-miss
  предлагается один раз (`resolveContinueOffer`).
- Партию пака стартует только «Играть» карточки уровня, а саму карточку можно
  открыть с главной, с карты и с карточки результата. Из `game` в `game` экран
  сменил бы `key` под живым рантаймом, а два рантайма одновременно жить не
  могут (см. «Жизненный цикл рантайма»). Двойной тап отсекается тем же
  правилом. Закрытая без старта карточка оставляет главную или карту, а над
  фоном прошлой партии (`result`) ведёт на главную.
- Следующий уровень и прогресс пишутся **до** показа карточки результата:
  «Дальше» и «Играть» с главной читают уже их.
- Стор, а не `useState` страницы: «Играть» живёт в отдельном компоненте
  (`MainActions`), а результат - в модалке вне дерева страницы. На
  размонтировании `Main` зовёт `goHome()` - уход со страницы (например, в
  редактор) партию обрывает, и возврат начинается с главной. Именно на
  размонтировании, а не на маунте: на маунте первый рендер успел бы
  смонтировать экран партии по старому стору, и рантайм поднялся бы только
  затем, чтобы тут же умереть.
- Правила - чистые функции с тестами в `features/match3Host` (слой вне
  главной: свой хост копии шаблона берёт их же, см.
  [custom-host.md](./custom-host.md)): `partyRules.ts`
  (`resolveStartLevelNumber`, `resolveNextLevelNumber`, `resolvePartyBoosters`,
  `resolvePreBoosterOptions`, `resolveContinueOffer`) и `levelProgress.ts`
  (прогресс, обучение, карта). «Первый уровень без бустеров» - правило игры, а
  не виджета: `resolvePartyBoosters(1)` и `resolvePreBoosterOptions(1)` отдают
  `[]`. Рантайм только прячет пустую панель
  (`widgets/game/model/areBoostersHiddenForParty`). Сценарий стора целиком
  покрыт `useMainFlowStore.test.ts`.

## Точки подключения

- **Триггер**: `MainActions` (`src/pages/main/ui/MainActions.tsx`).
  `pointerdown` «Играть» греет чанк экрана партии (`prefetchGameScreenChunk`),
  `click` зовёт `play()` - карточку уровня; чанк самой карточки `Main` греет
  на маунте. Там же «Уровни» (`openMap`) и ссылка «Редактор» на `/editor` с
  сохранением query (только при `__EDITOR_ENABLED__`).
- **Переключение экрана**: `src/pages/main/Main.tsx` рендерит
  `<GameScreenLazy />` вместо контента главной, пока в сторе есть `party`. Оба
  живут в колонке `.frame` (`app-frame`, на десктопе `360 / 700` высоты окна),
  а фон партии - сплошной цвет `--bg-game` на `.page` (`.pageParty`, экраны
  `game`/`result` - `isPartyScreen`) во всю ширину окна; карта уровней стоит
  на фоне главной; тот же цвет используется в превью редактора. Канвас рантайма
  прозрачен (`backgroundAlpha: 0`) за пределами доски.
  Фоновых картинок и звёзд нет, анимаций смены главная ↔ партия тоже нет.
- **Пауза**: `Main` передаёт `paused={useHasMountedModals()}`. «Дальше»/«Ещё
  раз» поднимают новую партию, пока над ней ещё доигрывает exit-анимацию
  карточка результата, - доска стоит на паузе, пока карточка не уйдёт из DOM
  (см. «Пауза под карточкой результата»).
- **Заглушка загрузки чанка**: `GameScreenLazy` даёт в Suspense
  `<GameLoadingShell />` (`src/widgets/game/ui/GameLoadingShell.tsx`) - тот же
  спиннер «Загрузка» на том же месте, что и в загрузочном состоянии
  `GameScreen`, поэтому подмена заглушки на реальный экран не читается как
  отдельный экран перехода. Приходящий спиннер `GameScreen` объявлен с
  `animateIn={false}`, иначе в момент подмены кольцо просело бы по яркости.
  Спиннер заглушки молчит для скринридера (`ariaLive="off"`) - иначе «Загрузка»
  прозвучала бы дважды подряд.
- **Экран партии**: `GameScreen` (`src/widgets/game/ui/GameScreen.tsx`). Одна
  партия - один маунт: рантайм поднимается на маунте через общий
  `widgets/game/lib/bootGameRuntime.ts` и уничтожается на размонтировании
  (см. «Жизненный цикл рантайма»). Уровень и бустеры читаются один раз, на
  старте рантайма, и кладутся в `levelConfigStore` (`setRuntimeLevelConfig`)
  до `bootGameRuntime`: модули читают их при создании. Смена пропсов посреди
  партии её не перезапускает. Контейнер канваса не содержит React-детей:
  `bootGameRuntime` чистит его (`replaceChildren`) и кладёт туда канвас Pixi.
- **Разрешение канваса**: канвас рисует в физических пикселях, а на экране
  занимает CSS-размер доски. `Application.init` получает `resolution` =
  `getRenderDpr()` (`widgets/game/configs/renderScale.ts`) и
  `autoDensity: true`, а `GameRuntimeCore.resize(cssWidth, cssHeight)` зовёт
  `renderer.resize(cssWidth, cssHeight, dpr)`: бэкбуфер - CSS-размер × DPR,
  стиль канваса Pixi пишет сам. Сцена при этом живёт в CSS px (`app.screen`),
  а вписыванием мира в экран занимаются модули по событию `resize` шины
  (общее правило `resolveSceneLayout`, см. «Отступы сцены»). Без DPR канвас
  рендерился бы в CSS-разрешении и растягивался на втрое более плотный экран -
  игра выглядела бы пикселизованной при том, что арт нарисован в 4x к
  дизайн-сетке 360x744. `RENDER_DPR_CAP` равен 3, то есть фактически не
  срезает ничего: кап 2.5 экономил бы fillrate ценой того самого, ради чего
  весь модуль и написан - на DPR-3 устройстве (440 CSS px доски) бэкбуфер
  выходил бы 1100 px против 1320 физических пикселей экрана, и композитор
  растягивал бы весь кадр на 1.2x. Фишка рисовалась бы в 128 px канваса и
  растягивалась до 154, хотя её исходник (168 px) на эти 154 хватает с
  запасом. Цена капа 3 - площадь бэкбуфера, fillrate x1.44; это единственное,
  что здесь надо мерить при регрессе FPS (перф-гейт в `low` опускает кап до
  1.5, см. «Перф-гейт»). CSS-размер канваса принадлежит Pixi - выставлять его
  из React нельзя, иначе он разойдётся с бэкбуфером и с тем, по которому Pixi
  переводит координаты указателя.
- **Разрешение печати текста** считается от `worldScale`, а не от DPR
  (`getTextResolution()`), и берётся геттером в момент создания текста
  (`lib/runtimeText`, `createRuntimeText`), а не константой модуля: канвас
  меряется уже после загрузки чанка игры, и константа навсегда осталась бы
  фолбэком по DPR. Растягивает текст именно `worldScale` - контейнеры сцены
  масштабируются им, и на 440 CSS px при DPR 3 это 3.67 против
  `ceil(DPR) = 3`, то есть текст остался бы единственным мыльным слоем на
  резком фоне. Стартовый размер канваса публикует не экран, а
  `bootGameRuntime()` - тот же владелец, что сбрасывает `GameStore`: он
  получает `canvasSize` (CSS-размер доски) в опциях, кладёт его × DPR в
  `renderScale` до `Application.init` и на `destroy` вызывает
  `resetRenderCanvasSize()`. Дальше размер обновляет
  `GameRuntimeCore.resize` (`setRenderCanvasSize`) на каждом ресайзе. Сброс
  обязателен: значение модульное, и без него партия, стартовавшая до первого
  замера доски, пекла бы текст по размеру канваса **прошлой** - ошибка
  молчаливая и зависящая от того, во что играли до этого.
- **Связка рантайм → React**: `widgets/game/model/useGameRuntimeEvents.ts`
  подписывается на `GameStore` и переводит переходы флагов в колбэки хоста.
  Колбэки читаются через ref: хост вправе передавать новые функции на каждый
  рендер. Модули рантайма пишут только флаги и про хост не знают.
  - `runtimeFailure` → `onError(reason)` (см. «Загрузка ассетов и отказ
    рантайма»);
  - `isExitRequested` → `onExitRequest()`. Флаг гасится сразу
    (`clearExitRequest`): он значит «нажали прямо сейчас», и без сброса
    повторное нажатие (хост решил не выходить) не дало бы перехода
    `false -> true`. Подтверждать выход или нет, решает хост; шаблонная
    главная выходит сразу;
  - `outOfMoves: 'none' -> 'pending'` → `onOutOfMoves(offer)` (см.
    «Near-miss»);
  - переходы стора (`diffStoreBoardEvents`) и события шагов
    (`model/boardEventBus`, их пишет `BoardStepPlayer` по
    `listStepBoardEvents`) → `onBoardEvent(event)` (см. «События партии для
    хоста»);
  - `isGameEnded && isFinaleFinished` → `onFinish({ isVictory, score, stars })`:
    очки - из `GameStore.score`, звёзды - `resolveLevelStars` по порогам уровня.
    Исход уходит ровно один раз на маунт (`isFinishedRef`), отладочные кнопки
    зовут тот же `finish`.

### Отступы сцены

Хост может отдать виджету отступы сверху и снизу (вырез, статус-бар,
home-индикатор): проп `insets={{ top, bottom }}` в CSS px или переменные
`--match3-inset-top` / `--match3-inset-bottom` на любом предке. Проп важнее
переменных, без обоих - `env(safe-area-inset-*)`; на обычной странице шаблона
это ноль. QA-флаг `?insets=47,34` прокидывает отступы с главной.

Поле любого размера (от 3×3 до 9×9) вписывается в ту же область сцены, что и
макетное 6×6: `lib/boardFit` (`resolveBoardFitScale`) ужимает поле крупнее
6×6 одним множителем по обеим осям, меньшие поля идут в макетном размере.
Множитель один на фишки (`GameLogic.handleResize`) и подложку
(`GameBoardBackground`), а порог свайпа и смещение за пальцем клетка берёт с
масштаба самого контейнера доски (`CellInputController.getBoardScale`).

- **Замер.** CSS-переменные холсту недоступны, поэтому внутри доски лежит
  пустой зонд `.safeArea`, растянутый от верхнего отступа до нижнего, и
  `lib/measureSceneInsets` снимает отступы с его бокса относительно доски.
  Меряет экран партии (`model/useGameRuntime`): на старте (в
  `bootGameRuntime({ insets })`, до сборки сцены) и в каждом `resizeCanvas`.
  Перемер будят ресайз окна, `ResizeObserver` на доске и зонде (хост поменял
  высоту или переменные) и смена пропа.
- **Хранение.** `configs/sceneInsets.ts` - модульное значение, как и
  `renderScale`: живой рантайм один. `bootGameRuntime` кладёт стартовые отступы
  и сбрасывает их на `destroy`; превью редактора их не передаёт - нули.
- **Раскладка.** Одно чистое правило `lib/sceneLayout.ts`
  (`resolveSceneLayout`, с тестами): безопасная зона = канвас минус отступы,
  `scale = min(width / DESIGN_WIDTH, safeHeight / DESIGN_HEIGHT)`, плюс `top`,
  `bottom` и `centerY` в координатах сцены. Сцена живёт в CSS px канваса
  (`autoDensity`), поэтому множитель «CSS px -> единицы сцены» у
  `GameRuntimeCore` - 1. Шапка (`ExitButton`, `MovesCounter`,
  `GameGoalsPannel`) меряется от `top`, низ (`BoostersContainer`) стоит на
  `bottom`, доска и её фон (`GameLogic`, `GameBoardBackground`) и укрупнённая
  цель интро (`GoalIntro`) - вокруг `centerY`. Тот же масштаб берут жест
  (`CellInputController.getBoardScale` - мировой масштаб контейнера доски) и
  разрешение текста (`getWorldScale`).
- **Одно событие.** Модули пересчитываются по событию `resize` шины рантайма
  (`IRuntimeViewport`: размер канваса и готовая раскладка): `useGameRuntime`
  после замера зовёт `runtime.resize(size)`, а `GameRuntimeCore.resize` шлёт
  событие и при прежнем размере канваса - смена одних отступов или качества
  доходит до модулей тем же путём. На паузе тикер стоит, поэтому ресайз сам
  рисует кадр (`app.render()`) - иначе под карточкой хоста остался бы пустой
  канвас.

Если бы масштаб считался от полной высоты, а отступ добавлялся только шапке, на
коротком экране с вырезом (375x667, 47 px сверху) плашка «Цель» наезжала бы на
первый ряд доски. Фон канваса при этом всё равно доходит до края экрана.

### Исход внутри рантайма

Что именно считать победой и поражением, решает `GameLogic.checkGameEndConditions()`,
и решает **один раз за партию**:

- Победа проверяется раньше поражения и исключает его: закрытые последним
  ходом цели - это выигрыш, а не «ходы закончились». Пока обе проверки стояли
  отдельными `if` без `else`, ветка `movesCount <= 0` перетирала уже принятую
  победу, и `finish` уходил с `isVictory: false`.
- Ранний выход по `isGameEnded` нужен по той же причине: метод вызывается
  после каждого хода, а повторный `setIsGameEnded` перезаписал бы `isGameWin`.
- «Все цели закрыты» - это `goals.length > 0 && goals.every(...)`. Пустой
  список целей не считается победой: `every` на пустом массиве вернул бы
  `true`, и партия завершалась бы победой на первой же проверке (целей нет
  между `resetStore` и `initGoals`, а также если в уровне нет `levelGoals`).

Прогресс целей списывает проигрыватель шагов (`BoardStepPlayer.registerGoals`)
по **тому же** правилу, что бот и тест каталога: `listGoalEvents(step)` из
`entities/game` (`lib/boardProgress`) - разрушенный слой клетки (предмет,
накладка, подложка), фишка, превращённая радугой, собранное «опусти вниз».
Поглощённая слизью фишка и фишка под предуровневым бустером в цель не идут.
Пока цели считали `destroy()` спрайтов, а бот - шаги, это были две реализации
одного правила, и уровни, откалиброванные ботом, могли разойтись с партией.
Цель засчитывается до проигрывания шага: копия спрайта (`flyCopyToGoalPanel`
у `BoardEntity` и `LayerEntity`) взлетает, пока сам спрайт ещё на доске -
спецфишка гасит свой синхронно, прямо в ударе. Полёт у всех один -
`IBoardFx.flyToGoalPanel` (`fx/createBoardFx`): к иконке своей цели
(`IBoardHud.getGoalTarget` -> `GameGoalsPannel.getGoalTarget`), стартовый
масштаб мировой (`getGlobalTransform`) - на ужатом поле
копия не крупнее оригинала. Копия видна весь путь, долетает размером иконки
(масштаб покоя из `getGoalTarget`, а не текущий спрайта - иконка может быть на
середине пульса) и растворяется в ней за последние 200 мс. Летит она над всей
шапкой, включая панель целей (`GOAL_FLIGHT_DEPTH` в `configs/sceneDepths`):
гасни копия с первого кадра и лежи она глубже слоя панели, до иконки
доходило бы невидимое и под панелью. Точка прилёта считается от безопасной
зоны: жёсткие `y = 40` уводили бы копии в вырез при `insets`.

Ход списывает `GameLogic.spendMove()`, а `refreshBoardState()` - пересчёт целей,
проверка конца партии и разбор тупика без списания хода. Бустеры зовут только
второй: бустер тратит собственный заряд, а не ход игрока (решай обе задачи
один вызов, применение любого бустера съедало бы ход).

`spendMove()` вызывается **до** анимации свапа, сразу после того, как
движок принял ход (`BoardEngine.trySwap` -> `accepted`), - иначе счётчик падал
бы примерно через секунду после жеста, и причина со следствием были бы
разорваны. Проверку конца партии это не сдвигает: `movesCount` она читает в
`refreshBoardState()`, то есть всё равно после всего каскада. Само списание
видно на экране - `IBoardHud.decreaseMoves()` -> `MovesCounter.decreaseCount()`
пульсирует цифрой (`BOARD_TIMING.moves.pulseMs`,
твин на тексте, а не на контейнере: подпись и подложка стоят на месте), а цвет
счётчика - производная от значения, а не эффект списания,
иначе уровень, начатый с трёх ходов, был бы белым.

Цифра и подпись под ней («ход»/«хода»/«ходов», `pluralizeRu`) анимируются
**разными** эффектами, и делить один объект между ними нельзя. Цифру ведёт
пульс - две половины подряд (`Quad.easeOut` вверх, `Quad.easeIn` вниз), и
новое число подменяется на стыке, на пике, когда оно крупнее всего: «минус ход» читается одним движением, а не подменой текста до начала
анимации. Подпись ведёт crossfade (`BOARD_TIMING.moves.fadeOutMs`/`fadeInMs`),
и только когда форма слова действительно другая (`2 хода` -> `1 ход`) - на
остальных ходах менять там нечего. Тяни crossfade и цифру тоже, он уводил бы
её в `alpha: 0` ровно на пике пульса, и пульс не был бы виден ни на одном
ходу - а `decreaseCount()` единственный путь, которым он вообще запускается.
Прерванный твин своих колбэков не доигрывает (цепочки идут через `motion.add`,
и следующая половина стартует только по честному концу предыдущей), поэтому
новый сначала применяет отложенное значение прерванного - иначе на быстрой серии ходов счётчик застревал бы на
промежуточном числе, а подпись - полупрозрачной. Мгновенный снап без анимаций
остаётся у `updateCount()`: его зовут `IBoardHud.init` (из
`GameLogic.initStates`, перенос счётчика с плейсхолдерного `0` на стартовое
число ходов уровня) и `refreshMoves` (добавочные ходы near-miss).

Активация спецфишки игроком (`handleSpecialActivateRequest`: одиночный тап по
спецфишке, `SpecialEntity.onTap`) держит `isProcessing` на всё время цепочки,
как и обычный свап. Если бы флаг там только читался, игрок успевал бы свапнуть
фишки в середине каскада, и два асинхронных цикла писали бы в один грид.
Тап хода не тратит.

Второй способ применить спецфишку - свапнуть её с любым соседом (фишкой или
спецфишкой; блокер и дыра - `blocked`). Ветка спецфишки в
`BoardEngine.trySwap` фигур не ищет: довёл игрок свайп до спецфишки - ход
состоялся, поэтому движок отдаёт `accepted` с шагом `swap` и взрывом, рантайм
списывает ход и проигрывает обмен (`playSwapStep`: анимация переезда, затем
запись грида) безусловно, а короткого отказа у этой ветки нет вовсе. Две
спецфишки дают комбинацию (см. [Спецфишки и комбинации](#спецфишки-и-комбинации)).

Сам флаг приватный, наружу торчит только чтение - геттер `GameLogic.isBoardBusy`,
а в стор уходит зеркало (`GameStore.isBoardBusy`, его пишет `setProcessing`).
Кнопки бустеров читают зеркало: модули друг друга по полям не трогают, а
реестр модулей ядра (`GameRuntimeCore.registerModule`) нужен только для
уничтожения - достать из него модуль по имени нельзя, зависимости передаются
конструктором.

### Ввод: слежение за пальцем, коммит на отпускании

Ввод клетки - `modules/cells/CellInputController` (отдельно от сущности и её
вида). Зона касания - пустой `Container` с `hitArea` (`Rectangle` по клетке,
`eventMode: 'static'`) в контейнере доски. `onPointerDown` открывает жест
(`beginDrag`) и ведёт спрайт за пальцем по доминирующей оси. Ход при этом
**не** заявляется: единственная точка коммита - `onGlobalPointerUp`.

Слежение и отпускание слушаются **на корне сцены** (`app.stage`:
`globalpointermove`, `pointerup`, `pointerupoutside`), а не на зоне клетки:
зона гаснет на время анимации клетки (`setEnabled(false)` ->
`eventMode: 'none'`), а жест, начатый до этого, обязан закрыться. Корень ловит
указатель по всему канвасу - у него `hitArea = app.screen`
(`GameRuntimeCore`), - поэтому отпускание над пустым местом канваса тоже
приходит `pointerup`.

Так было не всегда: какое-то время ход коммитился на пересечении порога. Это
снимало задержку длиной в жест, но отбирало право передумать - доска уезжала
под ещё не поднятым пальцем, и читалось это как баг, а не как отзывчивость.
Правило вернули к отпусканию сознательно; выигрыш по ощущению почти весь
остался, потому что его давало не раннее срабатывание, а само слежение: игрок
видит, что направление понято, с первого кадра.

Отсюда главное свойство ввода: **увести фишку за порог и вернуть палец обратно -
это не ход.** Судит только та точка, где палец поднялся.

**С выбранным бустером фишки не двигаются вовсе.** Пока бустер занесён, клетка -
цель применения, а не начало хода, и гейт двухрубежный. Первый рубеж - в
клетке: `enableBoosterMode()` поднимает `isBoosterMode` (`CellInputController`),
и `onPointerDown` по этому флагу выходит **до** `beginDrag()` и нажатия вида -
сброс нажатого масштаба живёт в `onGlobalPointerUp`, подписку на который ставит
только `beginDrag`, так что нажатие без жеста оставило бы фишку раздутой до
конца партии. Заодно не уходит и тап (`cellTap`): тап по спецфишке с занесённым
бустером применяет бустер (`boosterCellUp`), а не взрывает спецфишку.
Второй рубеж - `GameLogic.runSwapRequest`, гейт по `boosterMode.isActive`: он
ловит мультитач (палец уже вёл фишку, вторым пальцем тапнули кнопку бустера -
жест продолжается и на отпускании коммитит свап). Отклонённый так ход обязан
вернуть **обе** половины руками (`swapDrag.releasePartner(true)` +
`returnHome()`): `commitSwap` уже забыл смещение и передал эстафету
контроллеру, анимации свапа не будет. В буфер отложенного ввода он не
кладётся - игрок целился бустером, а не ходом.

Пара обменивается **целиком под пальцем**: `GAME_CONFIG.dragFollowTiles.swappable`
равен целой клетке, так что фишка доезжает до места соседа, а сосед - до её
места. Половина клетки (ровно порог) означала невидимую стену на середине жеста:
палец едет дальше, картинка стоит. Если соседа нет вовсе (край доски) или он не
свапается (блокер, дыра), ход укорочен до `dragFollowTiles.blocked` - четверти
клетки: жест остаётся живым, но пара не изображает обмен, которого не будет, и
фишка не ложится поверх блокера.

Порог коммита с этими числами не связан и остаётся на половине клетки: середина
пути - точка невозврата, а не конец движения. Меряется он по доминирующей оси -
и на отпускании, и при слежении: по длине вектора диагональный жест
засчитывался бы раньше, чем выглядит сдвинутым. Порог в пикселях сцены берёт
мировой масштаб контейнера доски (`getBoardScale` через `toGlobal`), а не
пересчёт раскладки: поле крупнее 6×6 ужато ещё и `lib/boardFit`.

**Ни в одном исходе пара не прыгает.** Перевалила середину - `commitSwap`
_забывает_ смещение, не трогая спрайты (`forgetDragOffset`, а на стороне соседа
событие `swapDragHandOff`), и `moveToCoords` внутри `swapTiles` доигрывает
только остаток пути: длительность считается от оставшегося расстояния
(`scaleToDistance`, пол - `BOARD_TIMING.swap.minDurationMs`), потому что полные
`durationMs` на последние проценты читались бы вязко. Довёл до конца - доезжать
нечего, сразу идёт каскад. Не дотянула - пара уезжает домой анимацией
(`returnHome`), а не телепортом. Будь сброс позиции частью общего сброса
визуала жеста, на отпускании пара телепортировалась бы в исходные клетки, чтобы
через кадр поехать через всю клетку заново - это и читалось бы как рывок в
момент коммита.

`returnHome()` обязателен и на путях, где ход отклонён **до** всякой анимации:
доска занялась каскадом (свайп ушёл в буфер), сосед оказался краем доски,
блокером или неподходящим партнёром лазера. Смещение к тому моменту уже передано
анимации свапа, а самой анимации не будет - без явного возврата фишка осталась бы
стоять мимо клетки до конца партии. Это касается **обеих** половин пары: в ветке
буферизации `handleSwapRequest` зовёт ещё и
`SwapDragController.releasePartner(true)`. Страховка «сбросить пару, когда доска
занята» живёт в `onGlobalPointerMove` и здесь не срабатывает: между моментом,
когда доска занялась, и отпусканием пальца может не прийти ни одного
`globalpointermove` - палец довёл фишку и замер.

Точка отсчёта жеста - место касания (`event.global`), а не центр спрайта: центр
включал бы в порог расстояние от пальца до середины клетки, и нажатие у правого
края требовало бы пройти пол-клетки лишних влево и почти ничего вправо.

**Отпускание за канвасом ходом не считается** ни при каком смещении
(`onGlobalPointerUpOutside` - только `returnHome` пары, без `commitSwap`). У
мыши такое отпускание приходит корню как `pointerupoutside`. Касание же
браузер неявно захватывает: палец, уехавший за край канваса, всё ещё
«принадлежит» ему, и отпускание приходит обычным `pointerup` - поэтому
`onGlobalPointerUp` сначала проверяет, что точка внутри экрана
(`app.screen.contains`), и иначе уходит в тот же путь «за канвасом». Без
`pointerupoutside` жест не закрывался бы вовсе: `releaseDrag()` не вызван,
`isDragging` залипает `true` - клетка больше не принимает ходов, а слушатели
корня продолжают дёргать фантомный свап из старых координат.

**Второй палец жест не ведёт и не закрывает**: `beginDrag` запоминает
`pointerId`, и события корня с чужим указателем игнорируются
(`isOwnPointer`); повторный `pointerdown` при открытом жесте новый не
открывает - лишняя подписка пережила бы жест, и один свайп отправлял бы
несколько `swapRequest`.

**Повисший жест закрывается тремя путями.** Открытый жест на доске один -
статик `CellInputController.activeDrag`. Новый легитимный `pointerdown`
закрывает чужой зависший жест тем же путём, что палец за канвасом (на iOS
WKWebView отпускание иногда не доходит вовсе: касание начали на DOM-заглушке
загрузки, а её узел убрали до `touchend`). Замок ввода рантайма закрывает его
хуком сброса: `GameLogic` регистрирует
`core.input.addResetHook(() => CellInputController.cancelActiveDrag())`, и
касание, открывшее DOM-слой хоста, не оставляет клетку «в руке» (см. «Пауза
под карточкой результата»). А `GameLogic.destroy()` и `bootGameRuntime()`
зовут `BoardEntity.resetActiveDrag()`: статик переживает партию и иначе унёс
бы ссылку на клетку мёртвой доски в следующую.

Геометрию пары считает не клетка: докуда можно уехать, зависит от соседа, а
соседа видно только по гриду. Контроллер ввода клетки отдаёт наверх сырой ход
пальца в дизайн-пикселях (событие шины `swapDragMove`), а двигает **обе**
половины через `BoardEntity.setDragOffset()` отдельная подсистема
`modules/SwapDragController.ts`. Позиция там считается от грида
(`getVisualCoords()`), а не прибавкой к текущей: у относительной арифметики
любая потерянная дельта становится вечной. Тот же довод, что у `fall()` и
`playRejectShake()`.

Сам клемп - чистое правило `lib/swapDragOffset.ts` (`resolveSwapDragOffset`)
с тестами, как `boardGravity`, `boardTempo` и `reshuffleLayout`: предел по
признаку «сосед свапается», раскладка по доминирующей оси, зеркальное смещение
партнёра. Ни Pixi, ни грид ему не нужны - кто сосед, решает вызывающий и
приносит одним булевым признаком.

Смещение сбрасывается на каждом пути выхода из жеста: `releaseDrag()` и
снятие клетки посреди свайпа (`CellInputController.cancelGesture()` - синхронно
в начале `destroy()`/`vanish()`, до анимации) проходят через
`BoardEntity.clearDragOffset()`.

Вторую половину пары двигает не клетка, а `SwapDragController`: ему нужен грид,
и `GameLogic` отдаёт доступ к нему колбэком. `CellInputController` эмитит в
шину `swapDragMove` (строка, колонка, направление, смещение), `swapDragEnd` и
`swapDragHandOff`, а контроллер держит ссылку на соседа, потому что сам сосед о
своём сдвиге не знает и вернуть себя на место не может. Подсистема живёт
отдельным модулем, а не методами `GameLogic`: тот и без неё держит ввод,
каскад, гравитацию, лазеры и три бустера. Сосед, который свапаться не умеет
(блокер, дыра) или которого нет вовсе (край доски), не двигается - зато сама
фишка за пальцем идёт всё равно: отказ честнее показать возвратом, чем мёртвым
жестом.

Пока доска занята каскадом, слежение за пальцем выключено. Свайп при этом не
теряется: на отпускании он уйдёт в буфер (см. ниже) и там же поднимет темп
рантайма. А вот смещение писало бы позицию спрайту, которым в тот же кадр
распоряжается твин гравитации: твин перетёр бы его покадрово, зато сброс в конце
жеста вычел бы смещение из твиновой координаты и оставил клетку стоять мимо
своей ячейки до конца партии.

Своей подсветки у выделенной фишки нет. `ICellView.bright` (`blendMode: 'add'`
плюс тинт `SKIN.colors.fx.cellBright`) осветляет весь квад текстуры, а не
рисунок, поэтому под фишкой проступал бы светлый квадрат; отклик на палец несут
увеличение (`ICellView.press`) и смещение. За наведённым бустером подсветка
осталась (`BoosterMode.handleCellOver` -> `brightCell()`) - там это
единственный признак «во что целюсь».

### Очередь ввода

Свайп и тап спецфишки, сделанные во время каскада, не теряются: их хранит
`modules/PendingBoardInput` (глубина - один ввод каждого вида, последний
побеждает), и на освобождении доски (`GameLogic.setProcessing(false)` ->
`flush()`) он переигрывает сначала тап, затем свайп через повторный
`handleSwapRequest` - валидность клеток при этом пере-проверяется сама. Пока в
буфере ждёт ввод, `GameLogic` ускоряет темп доски (`onPendingChange`).

Условия флаша - чистое правило `lib/pendingBoardInput.ts` (под тестами), одно
на оба буфера отложенного ввода: `canReplayPendingInput` (сущность жива в
гриде, партия не кончилась, рантайм не упал) для тапа спецфишки и
`canReplayPendingSwap` для свайпа. У свайпа есть **своё** дополнительное
условие: он доигрывается только с той клетки, с которой был сделан. Буфер
существует ровно потому, что идёт каскад, а каскад - это гравитация: фишка
почти наверняка уедет вниз, и переигранный «от её новой клетки» жест был бы
ходом в месте, которого игрок не выбирал, - причём ход за него всё равно
списался бы. Поэтому в буфере лежат и сущность, и `origin`-клетка: уехала
фишка - свайп отбрасываем, успел закончиться короткий каскад мимо её колонки -
доигрываем.

Порядок внутри `setProcessing(false)`: idle-эффекты армятся **до** флашей.
Флаш синхронно доходит до нового `setProcessing(true)` (`runGuarded` зовёт
сценарий синхронно, тот поднимает занятость до первого `await`), то есть
вложенный `disarm` случается внутри того же вызова - стой `arm` после флашей,
он бы его перетёр и заармил подсказку с дыханием на занятой доске.

### Финал партии на доске

Между решением об исходе и модалкой результата доска доигрывает финальную
сцену. На победе ей предшествует финальный бонус (см. «Финальный бонус»). Момент держит `GameLogic.playEndOfGameSceneIfReady()`, саму картинку -
`lib/endOfGameScene.ts` (`playEndOfGameScene`, композиция эффектов `IBoardFx`):
победа - вспышка, удар камеры `shockwave` и пауза `BOARD_TIMING.fx.winBeatMs`
под них (вспышка и удар идут покадрово на корне сцены и не ждутся, поэтому
длину финала задаёт именно пауза - без неё карточка победы приходила бы в тот
же кадр, что и вспышка). Конфетти на финале победы нет: несколько волн бёрстов
по случайным клеткам выглядели бы грязно и вдобавок держали бы модалку лишние
полсекунды. Поражение - удар `defeat` и затемнение доски (`IBoardFx.dimBoard`,
~0.6s). У поражения именно свой ключ в таблице `CAMERA_PUNCH`
(`lib/boardFxRules`), а не одолженный
`cascade`: правка силы каскада не должна молча менять концовку партии. Играет
сцена под занятым `isProcessing`, поэтому во время неё ввод закрыт.

React-слой отправляет исход только по паре `isGameEnded && isFinaleFinished`
(`useGameRuntimeEvents`; once-only держит `isFinishedRef`). Уходи исход
сразу по `isGameEnded`, модалка выскакивала бы поверх живой доски без
кульминации.

`refreshBoardState()` на законченной партии сразу уходит в сцену и не разбирает
тупик. Перерисовка панели целей и проверка исхода (`updateGoals()` +
`checkGameEndConditions()`) вынесены в `refreshGoalsPanelAndOutcome()` и зовутся
**дважды**: в начале (после хода) и после ветки перемешки. Одного вызова
мало: перемешка может принять раскладку с готовой тройкой (запасной слот, см.
ниже), каскад следом её разберёт, и если её фишки закроют последнюю цель
уровня, без второго вызова победа не зафиксировалась бы, пока игрок не сделает
ещё один ход. Шага там два, а не один
составной: прогресс целей уже лежит в сторе (его пишет `BoardStepPlayer`
по шагам хода, `listGoalEvents`), `updateGoals()` только
перерисовывает панель, а `checkGameEndConditions()` читает тот же стор напрямую
и от панели не зависит. Флаг исхода ставится единожды за партию, поэтому
повторный `refreshBoardState` сцену не перезапускает.

Сама перемешка предпочитает «чистую» раскладку - ход есть, готовой
комбинации нет: иначе доска сразу после шаффла взрывается каскадом, которого
игрок не просил. Раскладку «ход есть, но с готовой тройкой» держит запасной
слот и применяет, только если чистой за `RESHUFFLE_ATTEMPTS` попыток не
нашлось. Выбор - чистое правило `pickReshuffleLayout`
(`entities/game/lib/reshuffleLayout`, покрыто тестами), у движка остаётся
оценка кандидата: чтобы узнать про ход и комбинации, раскладку надо приложить
к его гриду (`BoardEngine.resolveDeadEnd`: `hasMove()` + готовая линия над
правилами `entities/game/lib/boardMatches`). Отсюда контракт правила: после
перебора грид держит последнюю _оценённую_ раскладку, а не выбранную, -
победителя движок применяет отдельным `applyChipLayout`. Случайность перебора -
зерно партии, как и у добора.

Вырожденная ветка «ход не построить даже вручную» (`stuck`: движок возвращает
доску в исходную раскладку) ставит поражение безусловно, и это не
упрощение: победой она кончиться не может. Цели проверены
вызывающим (при закрытых целях `refreshBoardState` вышел бы в финальную сцену
ещё до перемешки), а сама перемешка только переставляет фишки и ничего не
разрушает, так что прогресс целей за время её работы не двигается.

Флаг обязан подняться даже на сломанной сцене, иначе исход не уйдёт никогда:
партия останется законченной, но без `onFinish` и без карточки результата -
до перезагрузки. Поэтому `setFinaleFinished()` стоит в
`finally` вокруг сцены, а `releaseBoard` (аварийная разблокировка в
`runGuarded.onFailure`) поднимает его сам, если партия уже кончилась.

Из того же окна следует правило для выхода: пока сцена играет, `isGameEnded`
уже `true`, а `onFinish` ещё не ушёл. Выход в этот момент закрыл бы партию
поверх только что выигранной, поэтому `GameStore.exitButtonOnClick` на
законченной партии `isExitRequested` не поднимает: хост следом сам получит
исход.

### Спрайты клеток: сущность, вид и ввод

Клетка доски - три объекта с разными причинами меняться:

| Часть                                   | Владеет                                                                                                                                                                   |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `BoardEntity` (и наследники в `cells/`) | место на доске (`x`/`y`), смещение за пальцем; описание элемента (`look`); движение делегирует `CellMover`                                                                |
| `CellMover` (`cells/`)                  | переезд, возврат домой, дрожь отказа, падение по пути, вход добора                                                                                                        |
| вид клетки `ICellView` (`cells/views/`) | вся внешность на крючках: `create`, `appear`, `spawn`, `idle`, `press`/`release`, `pulse`, `bright`, `highlight`, `tint`, `hit`, `destroy`, `vanish`, `fallScale`, `land` |
| `CellInputController` (`cells/`)        | зона касания, свайп и тап, режим цели бустера, страховка от повисшего жеста                                                                                               |

Сущность выбирает реестр `BOARD_VIEWS` (`cells/boardViews.ts`: код движка ->
фабрика, все цвета фишек - вид `chip`). Наследник говорит, **что** рисовать:
`look()` - текстура по прочности, тинт стадии, масштаб, украшение покоя
(поворот ракеты, вращение радуги) и анимация разрушения (`destroy`: по
умолчанию `collapseMotion` - замах и схлопывание, у спецфишки
`burstMotion`, у ящика, камня и слизи - свои). **Чем** рисовать, решает скин
(`board.view` элемента) через реестр `CELL_VIEW_KINDS`
(`cells/views/cellViewKinds.ts`): `sprite` - `SpriteCellView` (текстура и
твины), `frames` - `FrameCellView` (тот же спрайт с покадровыми клипами на
крючках `idle`, `appear`, `hit`, `destroy`), `spine` - `SpineCellView`
(скелет Spine из ленивого чанка `spine`, анимации покоя по стадии,
появления, удара и разрушения; время - часы рантайма с темпом, см.
[skin.md](./skin.md#анимации-доски-и-темп)). Сущности от вида нужны только
позиция, масштаб, прозрачность и глубина (`TCellDisplay` - `Container` Pixi),
поэтому объект скелета подходит без правок сущностей. Твины вида и сущности
идут на часах рантайма (`core.motion`, `motion/displayMotion`: свойства
объекта и его `scale`-точка одной ручкой); покадровые клипы `FrameCellView` -
`AnimatedSprite` без своего тикера, кадры ведёт твин тех же часов, поэтому
пауза и темп доски действуют и на них. Неподвижные блокеры (ящик, камень,
слизь, дыра) касаний не принимают (`acceptsInput = false`) - зоны касания у
них нет вовсе.

`BoardEntity` **не рисует себя в конструкторе**. Рендер вызывает место
создания - оно одно: `createEntityFromPiece()` (`cells/EntityFactory`) для
стартовой доски и
для всего, что появляется в рантайме (добор шага `settle`, спецфишка шага
`special` или `transform`) - через `BoardStepPlayer.spawn`, который заодно
регистрирует спрайт по паспорту фишки. Вид тоже создаётся лениво, при первом
обращении: собственные поля наследников (`LaserEntity.direction`)
присваиваются уже после `super()`, и `look()` из конструктора видел бы их
`undefined` (вертикальный лазер не поворачивался).

Отсюда два правила:

- `render()` идемпотентен - он начинается с `disposeVisual()` (зона касания
  и объект вида со всеми его твинами, включая вращение радуги и подсветку).
  Через него же проходят все `destroy()`.
- Звать `render()` второй раз на той же сущности не нужно и нельзя.

Новая фишка въезжает через `enter(path)`: `placeAboveColumn()` переставляет
**свой** спрайт над верхней границей колонки, а не создаёт новый - иначе
каждая догенерированная за каскад фишка оставляла бы в контейнере мёртвый
объект.

Слои контейнера доски (`BoardStepPlayer`): подложки (`floorLayer`) под
предметами (`pieceLayer`), накладки (`overlayLayer`) над ними, эффекты
(лучи, кольца, попапы, частицы `fx/*`) - поверх всего в самом контейнере
(порядок отрисовки - порядок детей). Поэтому масштаб доски для порога свайпа
`CellInputController.getBoardScale()` берёт мировой (`toGlobal` контейнера
слоя), а не свой.

### Анимации шагов хода

Движок отдаёт ход протоколом шагов (`TBoardStep`), проигрыватель
(`BoardStepPlayer.play`) идёт по ним по порядку и ждёт анимацию каждого
целиком. Анимации - реестр, по функции на вид шага:

- `modules/steps/defaultStepAnimations.ts` - `DEFAULT_STEP_ANIMATIONS`,
  анимации по умолчанию. Тип - запись по всем видам шага (`TStepAnimations`):
  новый шаг движка без анимации не скомпилируется. Эффекты - методы
  `IBoardFx` (`context.fx`, реализация `fx/createBoardFx`).
- `modules/steps/stepAnimationOverrides.ts` - `STEP_ANIMATION_OVERRIDES`,
  **единственное место для своих анимаций в копии проекта**. Пустой в
  шаблоне.
- `modules/steps/resolveStepAnimations.ts` - слияние одно, при импорте
  проигрывателя.

Анимация получает контекст (`IStepAnimationContext`: ядро партии `core` - часы
и твины `core.motion`, шина, текстуры; контейнер доски, эффекты `fx`
(`IBoardFx`), шапка `hud` (`IBoardHud`), звук, акценты каскада, `board` -
зеркало доски спрайтами, `isDestroyed()`) и сам шаг. Переопределение получает
третьим аргументом `playDefault`:

```ts
// modules/steps/stepAnimationOverrides.ts
export const STEP_ANIMATION_OVERRIDES: TStepAnimationOverrides = {
  // дополнить: своё поверх анимации по умолчанию
  special: async (context, step, playDefault) => {
    await playDefault();
    context.fx.punchCamera('shockwave');
  },
  // заменить целиком: шаг без правок грида - только свой эффект и звук
  rowsBlast: async ({ core, container, sound }, { row, rows }) => {
    sound?.play('bomb');
    await playMyRowsWave(core.motion, container, row, rows);
  },
};
```

Замена целиком обязана сделать с гридом то же, что анимация по умолчанию
(`board.place`/`spawn`/`detach`/`vacate`): расхождение спрайтов с движком
ловит `assertInSync` в dev. Синхронная анимация (`damage`, `matches`,
`special`, `collect`) не задерживает протокол ни на кадр - не делайте её
ожидаемой без нужды, иначе ход станет длиннее. Цели (`registerGoals`), очки и
события хоста (`onBoardEvent`) считаются по шагу вне анимации - их
переопределение не теряет. Темп - не здесь, а в скине (`timing`).

### Эффекты доски

Всё, что рисуется поверх клеток и не принадлежит ни одной из них, - контракт
`fx/boardFx` (`IBoardFx`): частицы, вспышка, тряска, лучи ракет, волна бомбы,
полёт пропеллера, лучи радуги, эффекты бустеров, попап «×N», полёт копии к
цели, затемнение поражения. Анимации шагов, сущности и `GameLogic` только
зовут его в нужных точках. Реализация - `fx/createBoardFx` (одна на доску,
создаёт `GameLogic`), куски по темам - `fx/specialFx` (спецфишки и
комбинации), `fx/boosterFx` (бустеры), числа и правила без Pixi -
`lib/boardFxRules` (удары, тряска, вспышка, залп, кольцо, дуга, «×N» до 9, под
тестами). Хореография хода от реализации не зависит: промис каждого эффекта
резолвится через заданное время, а эффекты без промиса ход не задерживают
вовсе. Координаты - дизайн-координаты контейнера доски
(`lib/boardGeometry`), как у спрайтов клеток.

Обвязка - `fx/FxScene`: спрайты эффектов, учёт объектов и твинов, слои
частиц. Учёт ради жизненного цикла: эффект живёт дольше хода (попап, хвост,
полёт к цели, кольца луча), и `destroy` снимает сначала твины, затем объекты,
слои частиц и уборку `onDispose` - Pixi бросает на записи в уничтоженный
объект, а твин, доигрывающий по снятому спрайту, ронял бы кадр часов
рантайма.

- **Частицы** - `fx/ParticleLayer`: один `ParticleContainer` Pixi v8 (одна
  текстура, один вызов отрисовки на слой) и пул `Particle`; физика - чистое
  `lib/particleMotion` (`{min,max}` на рождении, `{start,end}` по доле жизни,
  гравитация, зона рождения, `maxAlive`, поток `advanceParticleFlow`). Своего
  тикера у слоя нет: кадр двигает `FxScene` с часов рантайма
  (`RuntimeMotion.onFrame` с `timeScale: 'ignore'` - пауза останавливает,
  темп доски не ускоряет, см. «Часы и твины рантайма»).
- `emitDestroyBurst()` - сноп частиц цвета элемента (`particle`, тон -
  `lib/destroyTint`: `getElementDestroyTint` скина, иначе
  `colors.fx.burstDefault`). Слой снопа **один на доску** и поднимается
  наверх контейнера на каждый выстрел: каскад с прошлого снопа дописал в
  контейнер новые фишки, и частицы ушли бы под них. Вызов один на все клетки -
  `burst()` в контексте разрушения вида клетки (`destroyContext`): анимация
  разрушения элемента решает, когда выпустить частицы, но не как. В
  качестве `low` частиц вдвое меньше.
- `createFallTrail()` - смаз падения на три строки и длиннее: общий слой,
  частица остаётся там, где её оставила фишка, шаг - полклетки, потолок живых
  частиц 120 (предохранитель fill-rate на поле крупнее 6×6); в качестве `low`
  хвоста нет.
- Хвост летящего спрайта (шар бустера, пропеллер) - `FxScene.createFlightTrail`:
  свой слой на пролёт, кладётся в контейнер **до** спрайта (след идёт под
  ним), после `stop` живёт, пока не догорит последняя частица.
- `showComboPopup()` - «×N» множитель каскада со второй итерации (шаг
  `matches` движка, `modules/CascadeAccents`), текст - `createRuntimeText` и
  `GAME_TEXTS.fx.comboMultiplier`. Куда его ставить, решает чистое правило
  `lib/comboAnchor.ts`: якорь - центр масс **самой крупной комбинации**
  текущей итерации, а не клетка, с которой начался ход - иначе попап
  застревал бы на месте первого свапа всю цепочку каскада вместо того,
  чтобы идти за фишками, которые реально гаснут на второй, третьей...
  итерации. В правило уходят именно группы (линии звена из шага `matches`,
  длинные первыми, - их собирает движок из `findBoardMatches`), а не плоский
  список всех сгоревших клеток: на одной итерации каскад нередко гасит две
  несвязанные тройки у противоположных краёв доски, и общий центр масс
  поставил бы «×N» ровно между ними - в клетку, где не происходило ничего.
  Пустой список групп (в реальном цикле недостижимо - каскад движка заходит в
  итерацию только когда есть совпадения) даёт откат в центр поля.
- Хайп-фраза каскада («ОБА-НА!» и т.п.) - DOM-оверлей по центру игрового поля
  (`ui/ComboPhraseBanner.tsx`, Figma node `18938-26622` - оверлей растянут на
  весь `.board`, флекс-центр совпадает с центром доски), не текст холста:
  нужен CSS-перенос на 2 строки и типографика по макету (сплошная белая
  заливка глифов плюс сиреневая обводка под ней через `-webkit-text-stroke` с
  `paint-order: stroke`). Длинную фразу («Феноменально!») баннер меряет в одну
  строку и ужимает кегль под ширину (`lib/comboPhraseFit.ts`, чистое правило с
  тестом), ниже предела перенос отдаётся CSS. Показывается на том же пороге
  итерации, что и «×N», но реже - вероятностный ролл плюс кулдаун от прошлого
  показа (`BOARD_TIMING.comboPhrase`, чистые правила - `lib/comboPhrases.ts`),
  иначе длинная цепочка сыпала бы фразами на каждом звене. Рантайм только
  решает «когда и какую» и публикует текст в мост-стор
  `store/comboPhraseStore.ts` (рантайм -> React через модульный стор); время
  жизни карточки на экране и её анимацию входа/выхода ведёт сам
  `ComboPhraseBanner`. Он же чистит стор на размонтировании, а
  `bootGameRuntime` - на старте рантайма: стор модульный, а таймер показа
  живёт внутри баннера, поэтому экран, ушедший во время показа
  (подтверждённый выход, сбой рантайма, превью редактора уровней без баннера),
  оставил бы фразу висеть до перезагрузки и следующая партия открылась бы с
  ней на первом кадре.
- `punchCamera()` - удар по таблице `CAMERA_PUNCH` (`lib/boardFxRules`:
  `cascade` для глубокого каскада, `strike` для лазера и грави-луча,
  `colorSweep` для залпа порталов, `shockwave` для волны шара и финала победы,
  `defeat` для финала поражения). Длительность и сила (доля размера экрана)
  лежат одной таблицей, чтобы эффекты сравнивались в одном месте. Камеры у
  Pixi нет: тряска - смещение корня сцены (`app.stage.position`), новое
  случайное на каждый кадр (`resolveShakeOffset`), поэтому трясётся и шапка;
  удар во время удара не перебивает. Порог каскада для тряски - свой
  (`CascadeAccents.emphasizeDeepCascade`), не завязанный на порог попапа.
- `flashBoard()` - белый прямоугольник на весь экран в корне сцены
  (`CAMERA_FLASH_DEPTH` в `configs/sceneDepths`, над полётом цели; запас 5% за
  краем под тряску), цвет - `colors.fx.flash` скина, гаснет линейно 1 -> 0
  за `flashMs`.
- `flyToGoalPanel()` - копия засчитанного спрайта летит к иконке своей цели в
  корне сцены над шапкой (`GOAL_FLIGHT_DEPTH`); старт - мировые место и масштаб
  (`getGlobalTransform`), цель - `IBoardHud.getGoalTarget`, без неё - середина
  верха безопасной зоны (см. «Исход внутри рантайма»).
- Волна шара обрезается маской-полосой на контейнере волн, шар улетает за
  правый край сцены, переведённый в координаты контейнера доски (`toLocal`).
- Пресс-фидбек фишки и squash при приземлении - твины, но не через
  `motion.killTweensOf(image)`: ссылка на свой твин лежит в виде клетки
  (`scaleTween` у `SpriteCellView`/`SpineCellView`), и гасится только он.
  `killTweensOf` снял бы со спрайта и чужие твины (падение, спавн, свап) -
  промис падения резолвился бы досрочно (`onInterrupt`), а фишка навсегда
  осталась бы висеть мимо своей клетки. Поймать это можно тапом по доске во
  время осыпания: спавнящаяся фишка интерактивна.
- Тайминги доски не живут константами по файлам: все числа - в
  `configs/timing.ts` (`BOARD_TIMING`), всё, что из них считается, - в
  `lib/boardTempo.ts` (см. [Темп доски](#темп-доски)). Исключение -
  `CAMERA_PUNCH` в `lib/boardFxRules.ts`: она держит длительность в паре с
  силой, и вынос одних длительностей разорвал бы удар пополам.
- Цвета эффектов - только `SKIN.colors.fx` (литералов цвета в `fx/*` нет).

### Звук

Своих аудиофайлов у шаблона нет: звуки синтезируются на лету из осцилляторов
и шума. Рецепты и чистые правила - `widgets/game/audio/soundRecipes` (с
тестами): голоса с огибающей и глиссандо, высота «плинка» матча по шагу
каскада (`resolveMatchNote`: на тон за звено, не выше октавы), отметки
предупреждения о ходах (`shouldWarnLowMoves`: 5, 3, 1) и такт фоновой музыки
(`buildMusicBar`: мягкое арпеджио I-vi-IV-V с басом). Словарь событий
(`TSoundCue`) и формат рецепта - контракт скина (`entities/skin`): скин
переопределяет рецепт любого события (`ISkinManifest.sounds`), остальные
звучат рецептами по умолчанию (`resolveSoundRecipe`). Звук удара по элементу
тоже из скина - `board.hitSound` описания элемента (треск у блокеров и
накладок, `playHitSound` в `steps/defaultStepAnimations`).

Играет их `audio/SoundEngine` - модуль рантайма `sound`, регистрируется
первым (кнопка звука и доска берут его при создании). Контекст свой
(`AudioContext`, у старого Safari - `webkitAudioContext`) и ровно на одну
партию: создаётся и разблокируется первым жестом игрока (`pointerdown`,
`touchend` или `keydown` на `window`, в фазе захвата), а `destroy` его
закрывает - Safari держит лишь несколько живых контекстов на страницу. Пока
звук не разрешён, звуки не копятся, а пропускаются - иначе первый тап
выстрелил бы всем накопленным разом. Без WebAudio партия идёт молча.

Кто что озвучивает:

- `BoardStepPlayer` - свап, звено каскада, рождение и превращение
  спецфишек, взрывы (`BLAST_SOUND` по виду взрыва), бустеры, треск блокеров,
  перемешка;
- `GameLogic` - отказ свапа, старт музыки после интро, фанфара или спуск на
  финале (музыка там же останавливается);
- сам `SoundEngine` по подписке на `GameStore` - тик цели и закрытие цели,
  предупреждение о малом остатке ходов.

Музыка планируется по часам аудиоконтекста на полторы секунды вперёд
(`MUSIC_LOOKAHEAD_SECONDS`), таймер плана - оконный (`setInterval`, 300 мс), а
не часы рантайма: темп рантайма ускоряется под буферизованный ход, а музыка
ускоряться не должна; таймер снимает `destroy`. Потому же таймер сам с
тикером не встаёт, и пауза партии (проп `paused` - слой хоста, подсказка
механики) глушит музыку явно: модуль слушает события `pause`/`resume` шины
рантайма, снимает план и гасит выход спадом, а на `resume` продолжает с того
же такта. Частые звуки
ограничены паузой (`CUE_COOLDOWN_MS`): залп по строке не превращает восемь
тресков в шум.

Кнопка звука - `modules/SoundToggle`, в левом нижнем углу на линии панели
бустеров (в шапке на 360 дизайн-px места нет), в стиле кнопки выхода; иконки -
процедурные `soundToggleOn`/`soundToggleOff` на той же плашке, что выход
(скин: `skins/default/art/hudArt`). Выбор запоминается в `localStorage`
(`audio/soundPreference`, ключ `match3-pixi:sound-muted`); недоступное хранилище
означает «звук включён», а не сбой. Тактильного отклика в игре нет.

### Подсказка в тупике

Когда ходов фишками на доске нет (`BoardEngine.resolveDeadEnd` ->
`specialHint`), `refreshBoardState()` подсвечивает первую спецфишку
(`SpecialEntity.highlightSpecial()`) как единственный выход - сработает она
обычным тапом. Подсветка - бесконечный tween (`repeat: -1`), поэтому её
жизненный цикл явный: `GameLogic.highlightedSpecial` держит ссылку, а
`clearSpecialHighlight()` гасит подсветку, как только ходы вернулись,
спецфишка активирована или ушла с доски (`BoardStepPlayer` сообщает об этом
колбэком `onEntityDestroyed`). Сам `highlightSpecial()` идемпотентен - иначе
каждый ход в тупике вешал на тот же спрайт ещё один вечный tween.
`unhighlightSpecial()` останавливает именно свой tween: `killTweensOf(image)`
снёс бы заодно падение фишки - его промис резолвился бы досрочно
(`onInterrupt`), и фишка осталась бы стоять мимо своей клетки.

### Подсказка простоя

Если доска свободна (`setProcessing(false)`) и игрок пять секунд ничего не
делает, `modules/IdleHint.ts` пульсирует пару с лучшим ходом - лёгкий
пульс на самих фишках, не подсветка спецфишки в тупике. Пару ищет
`GameLogic.resolveIdleHintPair()` через `BoardEngine.findBestMove`: из всех
ходов, которые движок примет (`listMoves`), - самая ценная фигура (радуга >
бомба > ракета > пропеллер > тройка) или свап спецфишки (комбинация двух -
ценнее всего), при равенстве - больше клеток, нужных цели уровня
(`isPriorityTarget`), затем ближе к центру поля. Ход меряется фигурой сразу
после обмена, без каскада: подсказка не подглядывает в добор. Первый
найденный ход (`findHint`, `entities/game/lib/findHintMove.ts`) остался у
движка для тестов и редактора.

С подсказкой на одном жизненном цикле и одном гейте живёт сосед
`modules/IdleBreathing.ts`: раз в 4-6 секунд случайная фишка едва заметно
дышит по **alpha** (доска читается живой в покое). Целевое свойство выбрано
сознательно: scale фишки уже владеет собственный scale-твин вида клетки (пресс, squash, пульс
подсказки), а alpha в покое не владеет никто - вне покоя ею распоряжаются
въезд (`enter`) и разрушение (`ICellView.destroy`), но на занятой доске
дыхание снято. Спецфишки не дышат вовсе - их alpha владеет подсветка тупика
`highlightSpecial`. Обе подсказки читают одно состояние через
`GameLogic.resolveIdleGatesOpen()` (то же чистое правило), arm/disarm идут
пунктом с `setProcessing`.

Гейт вынесен в чистое правило `lib/canShowIdleHint.ts` (под тестами): занятая
доска (`isProcessing`), законченная партия, сбой рантайма и партия, которая
ждёт решения хоста на исходе ходов (near-miss). Дыхание вдобавок выключено в
низком качестве отрисовки (перф-гейт).

Жизненный цикл явный: таймер - `motion.schedule` на часах рантайма (умирает
вместе с рантаймом и стоит на паузе), а пульс играет сама клетка
(`BoardEntity.playIdlePulse`/`stopIdlePulse` -> `ICellView.pulse`) через
собственный scale-твин вида. Пульс со стороны был бы вторым писателем в
`scale` мимо владельца, а остановка твина не откатывает значение - снятие
пульса явно возвращает масштаб покоя (`killTweensOf` здесь снёс бы со
спрайта падение/свап). Любое `setProcessing(true)` и любой `pointerdown` на
корне сцены гасят подсказку;
`pointerdown` к тому же перезапускает отсчёт. На закрытом гейте отсчёт не
перезапускается сам: состояние от этого не изменится, а новый отсчёт всё равно
придёт с ближайшим освобождением доски или тапом. Это правило общее для обоих
модулей - `IdleBreathing` на пустом `pickChip()` тоже разоружается, а не
перезапускает таймер: иначе на законченной партии он будил бы рантайм каждые
4-6 секунд до конца жизни рантайма. Разборка - `IdleHint.destroy()` и
`IdleBreathing.destroy()` в `GameLogic.destroy()`.

### События партии для хоста

`IGameScreenProps.onBoardEvent(event)` - необязательный колбэк с фактами
партии для аналитики, вибрации, своих звуков и ачивок. На ход партии он не
влияет. Тип - `TBoardEvent` из баррели `@/widgets/game` (без Pixi):

| `type`           | Когда                                                  | Поля                                                               |
| ---------------- | ------------------------------------------------------ | ------------------------------------------------------------------ |
| `moveMade`       | ход игрока засчитан (свап, тап спецфишки), до анимации | `movesMade`, `movesLeft`                                           |
| `cascade`        | звено каскада (шаг `matches`)                          | `iteration` (с единицы), `groups`                                  |
| `specialCreated` | спецфишка родилась                                     | `kind`, `col`, `row`, `source`: `match` / `transform` / `preBoost` |
| `goalProgress`   | шаг цели уровня                                        | `id`, `current`, `target`                                          |
| `goalCompleted`  | цель закрыта, один раз на цель                         | `id`                                                               |
| `boosterUsed`    | заряд бустера списан                                   | `kind`, `left`                                                     |
| `scoreChanged`   | очки выросли (по шагу, вместе с анимацией)             | `score`, `delta`                                                   |

Выводятся из протокола хода и `GameStore`, а не из спрайтов: события шагов -
чистое `listStepBoardEvents` (`model/boardEvents`, реестр `STEP_BOARD_EVENTS`
по виду шага, без `switch`), их пишет
`BoardStepPlayer.play` в канал `model/boardEventBus` до анимации шага;
события стора - чистое `diffStoreBoardEvents` по переходу (только рост:
сброс стора между партиями, пересчёт ходов в финальный бонус и добавочные
ходы хоста событий не дают; ход считает `GameStore.movesMade`, его
увеличивает `GameLogic.spendMove`). Переопределённая анимация шага или другой
вид клетки событий не теряет. Переводит всё в колбэк
`useGameRuntimeEvents`, как и остальные колбэки хоста.

### Очки и звёзды

Очки - чистое правило по протоколу хода `entities/game/lib/boardScore.ts`
(`scoreBoardSteps`, под тестами), то же, что считает бот: фишка в фигуре -
`20 × звено каскада`, фишка под взрывом, бустером или превращённая радугой -
30, удар по блокеру или слою - 50, рождённая спецфишка - 120-300, собранное
«опусти вниз» - 500, ход финального бонуса - 250. Звено удар узнаёт по
следующему шагу: движок пишет урон фигур и сразу за ним `matches`.
Начисляет очки `BoardStepPlayer.play` - по шагу, вместе с анимацией
(`GameStore.addScore`), а не скачком в конце хода.

Звёзды: первая - за победу, вторая и третья - пороги `starScores` уровня,
правило `resolveLevelStars` (`entities/game/lib/levelStars.ts`). Поражение
звёзд не даёт. Звёзды необязательны: у уровня без `starScores` исход несёт
`stars: null`, шкала под доской - подпись «Очки: N» без полосы (`formatScoreMeterText`), карточка
победы - только очки, карта уровней - только номер. В партии -
строка под доской (`modules/ScoreMeter`): полоса до третьей звезды с запасом
(`lib/scoreMeter`), три звезды на порогах и число; вторая и третья горят по
очкам и до победы, первая - на закрытых целях. Исход уходит хосту с очками и
звёздами (`IGameOutcome`), карточка победы рисует их (`ResultStars`).

### Финальный бонус

Победа с запасом ходов доигрывает «Sugar Crush» до концовки
(`GameLogic.playVictoryBonus`): `BoardEngine.playFinale(movesLeft)` отдаёт шаг
`bonus` (счётчик ходов быстро тикает в ноль, звук `bonus`), превращение
случайных свободных фишек в ракеты (`transform`, до `MAX_FINALE_ROCKETS = 10`,
остальные ходы идут только в очки) и их залп одной цепочкой, а затем по
очереди срабатывают спецфишки, оставшиеся на доске. Цели уже закрыты, поэтому
бонус - только очки и зрелище; доска на это время идёт в
`BOARD_TIMING.finale.speedUp` (1.7) раза быстрее (`RuntimeMotion.setTimeScale`:
твины и задержки; частицы, тряска и вспышка - в своём темпе). Тревога «мало
ходов» на законченной партии молчит (`SoundEngine`).

### Near-miss: ходы кончились, цели нет

Хост, который передал `onOutOfMoves`, решает исход сам: на нуле ходов при
незакрытых целях `GameLogic.checkGameEndConditions` не ставит поражение, а
переводит `GameStore.outOfMoves` в `pending`; мост зовёт
`onOutOfMoves({ goalsLeft, continueWith, giveUp })`. Пока решения нет, ход,
тап и бустер не принимаются, подсказки простоя молчат, разбор тупика ждёт.
`continueWith(n)` добавляет ходы (`continueParty`) - доска разбирает тупик и
партия идёт дальше; `giveUp()` (`declineContinue`) - поражение с финальной
сценой. Решение принимается один раз: двойной тап по кнопке хоста ходов
дважды не добавит. Без колбэка (наличие читается на старте,
`partyOptions.offersContinue`) - поражение сразу.

Шаблонный хост показывает карточку `outOfMoves` («Ещё чуть-чуть!», цели,
«+5 ходов» / «Сдаться») один раз за партию (`resolveContinueOffer`); второй
исход ходов - сразу `giveUp()`. Валюты у шаблона нет, и бесплатное
продолжение без предела отменило бы цену хода.

### Ход двумя тапами

Кроме свайпа, ход делается двумя тапами (`lib/tapSelection`, под тестами):
тап по фишке выбирает её - белая рамка дышит над клеткой; тап по соседней
подвижной клетке - ход (свап спецфишки и комбинация двух - тоже); повторный тап
снимает выбор, тап по дальней фишке перевыбирает, по спецфишке без выбора -
взрыв. Тап любой клетки приходит одним событием `cellTap` (`CellInputController.onGlobalPointerUp`
-> `GameLogic.handleCellTap`): что двигать, знает движок (`canSwapAt` -
накладки и блокеры), клетка - нет. Выбор снимается на занятии доски, свайпе,
старте бустера и уходе выбранной клетки с доски; на занятой доске тап не
выбирает (свайп в это время буферизуется, а тап - ещё не ход).

Тап по спецфишке - **ход**, как в Royal Match: он списывает ход (`spendMove`)
и будит слизь. Бесплатный тап делал спецфишку чистым бонусом поверх хода и
ломал баланс уровней.

### Предуровневые бустеры

Ракета, бомба и радуга, выбранные на карточке уровня, приходят пропом
`preBoosters`. После сборки доски (`GameLogic.placePreBoosters`, до первого
хода) движок ставит их на случайные свободные фишки (`placeStartSpecials`,
шаг `preBoost`): фишка уходит без разрушения - не в цель и не в очки, -
спецфишка выскакивает на её месте со вспышкой.

### Обучение механике при первой встрече

Тонкий контракт: хост передаёт `tutorial` - механики уровня, которых игрок ещё
не видел (`listLevelMechanics` от уровня минус знакомые из прогресса), - а
виджет после интро (`GameStore.isIntroFinished`) показывает по подсказке на
каждую (`ui/MechanicTip`, текст и иконка - описание элемента в скине,
`getMechanicTip`/`getElementIcon`): иконка та же, что в палитре редактора,
правило в одну фразу, «Понятно» (фокус переходит на кнопку). Очередью
подсказок владеет хук `model/useMechanicTips` (`currentTip`, `isBlocking`,
`dismiss`), `GameScreen` только раскладывает его. Пока подсказка видна,
партия стоит на паузе (`paused` рантайма), «Понятно» зовёт
`onTutorialSeen(mechanic)` - хост запоминает механику и в следующих партиях
её не передаёт.

### Перф-гейт

Слабый Android упирается в fill-rate бэкбуфера, поэтому качество отрисовки
двухступенчатое (`configs/renderQuality`): `high` - полное, `low` - кап DPR
1.5 вместо 3 (вчетверо меньше пикселей на DPR-3 экране), вдвое меньше частиц
разрушения, без хвостов падения и дыхания фишек. Правила доски, анимации хода
и звук не меняются.

- `modules/PerfMonitor` раз в секунду берёт FPS тикера Pixi - кадры окна,
  делённые на его длительность, а не мгновенный `ticker.FPS` (на паузе тикер
  стоит, и замера нет; кадр длиннее окна или скрытая вкладка - разрыв, окно
  начинается заново) - и пишет его в `GameStore.fps`.
  Решение - чистое правило `lib/perfGovernor`: первые три замера не в счёт,
  дальше четыре секунды подряд ниже 40 FPS понижают качество - один раз на
  партию. Канвас под новый DPR пересобирает `useGameRuntime` (подписан на
  `GameStore.renderQuality`).
- Качество пишется одной функцией `lib/applyRenderQuality` - модульное
  значение для отрисовки и зеркало в `GameStore` для React-слоя. Стартовое
  выставляет `setRuntimeLevelConfig` из режима партии (`partyOptions.quality`)
  ещё до замера канваса, от которого зависит DPR; `resetStore` зеркало не
  перетирает, а повторяет.
- Режим от хоста - проп `quality` (`auto` по умолчанию; `high`/`low`
  фиксируют качество и выключают гейт). Шаблонная главная берёт его из
  QA-флага `?perf=low|high`. Отладочная панель (`?gameDebug=true`) показывает
  FPS и текущее качество.
- Движок под бюджетом скорости: `BoardEngine.perf.test.ts` - 300 ходов с
  лучшей подсказкой на поле 9×9 (ход разыгрывается синхронно до анимации, и
  каждая миллисекунда там - задержка отклика на слабом телефоне). Тест в
  проекте vitest `slow` (`npm run test:slow`, CI - `test:ci`): бюджет по часам
  в watch-режиме `npm test` мигал бы.

Ручной гейт перед релизом - на живом бюджетном Android (Android 10, 3 ГБ ОЗУ,
DPR 2-3): партия уровня 29 (поле 9×9, пять цветов) под
`?gameDebug=true` - медиана FPS во время каскадов и комбинаций не ниже 50,
перф-гейт не должен срабатывать на `?perf=high`-сравнении больше чем на
просадку от каскада; профиль - Chrome remote debugging, вкладка Performance.
С `?perf=low` та же партия обязана держать 55-60 FPS.

### Жизненный цикл рантайма

Единственное место, где создаются `Application` Pixi и ядро партии, -
`widgets/game/lib/bootGameRuntime.ts`. Экран партии и превью в редакторе
уровней зовут именно его: копия этой последовательности у редактора отставала
бы от боевой на каждую правку доски, и превью показывало бы не ту игру,
которую видит игрок. Наружу он отдаёт `IGameRuntime` - `setPaused`,
`setInputEnabled`, `resize`, `destroy`; ссылки на движок отрисовки у экрана
нет.

Экран партии (`ui/GameScreen.tsx`) - только разметка доски. Рантаймом
владеет хук `model/useGameRuntime`: старт и уничтожение, CSS-размер канваса
по доске (`lib/resolveCanvasCssSize`, общий с превью редактора) и отступы,
пауза и ввод. События рантайма переводит в колбэки хоста
`model/useGameRuntimeEvents`, отладочные кнопки - `ui/GameDebugActions`.

**Последовательность `bootGameRuntime`:**

1. Сброс прошлой партии: `GameStore.resetStore()`, мост-стор хайп-фразы,
   открытый жест клетки (`BoardEntity.resetActiveDrag`), DOM-контейнер
   (`replaceChildren`), модульные `renderScale` (стартовый `canvasSize` × DPR
   или сброс) и `sceneInsets`.
2. Параллельно (`Promise.all`): `Application.init` (`preference` - см.
   «Рендерер: WebGPU и WebGL», `backgroundAlpha: 0`, `antialias`,
   `resolution` = DPR, `autoDensity`, стартовый CSS-размер доски - иначе Pixi
   поднял бы бэкбуфер под дефолтный размер и тут же пересоздавал его,
   `autoStart: false` - рисовать до сборки сцены нечего), загрузка файлов
   скина (`loadSkinTextures`), шрифт текстов холста (`waitGameFonts`) и
   скелеты Spine (`loadSpineSupport`, только если в скине есть вид `spine`).
3. Подписка на потерю контекста (`watchRendererContext`) и фактический
   рендерер в стор (`GameStore.rendererKind`).
4. Битый файл или скелет - `failRuntime('assets')`, сцена не собирается.
   Иначе канвас - в контейнер, процедурные текстуры
   (`registerProceduralTextures`), ядро `GameRuntimeCore` и модули в порядке
   регистрации: звук, кнопка звука, панель целей, выход, счётчик ходов, шкала
   очков, перф-монитор, панель и кнопки бустеров, последней - доска
   (`GameLogic`: она собирает ходы и цели в стор и подписывается на
   `boosterStart`, который кнопки эмитят только по клику).
5. Стартовый ресайз, затем первый **отрисованный** кадр снимает
   `isGameLoaded`: слушатель `ticker.addOnce` с приоритетом
   `UPDATE_PRIORITY.UTILITY` идёт после отрисовки приложения (`LOW`). Пауза,
   пришедшая во время загрузки, ложится сразу после этого кадра - иначе под
   карточкой хоста остался бы пустой канвас.

Init асинхронный, поэтому `destroy` может прийти раньше него: рантайм
помечается уничтоженным, а приложение гасится, как только init вернётся, -
уничтожать `Application` до конца `init` Pixi не умеет. Init без единого
рендерера (ни WebGPU, ни WebGL) - `failRuntime('context-lost')`: графики нет,
для хоста это тот же исход, что невосстановленный контекст.

**Ядро - `core/GameRuntimeCore`**, передаётся модулям **явно** -
конструктором, глобала нет: модуль умирающей партии физически не может
дотянуться до ядра следующей. Ядро держит приложение, слои, часы и твины
(`motion`), шину (`events`), текстуры (`textures`), замок ввода (`input`),
поддержку Spine (`spine`, `null` без вида `spine` в скине) и реестр модулей
(`registerModule`, только для уничтожения). Часы рантайма подписаны на тикер Pixi с
`UPDATE_PRIORITY.HIGH` - раньше отрисовки, чтобы кадр рисовал уже сдвинутые
твины; исключение из твина ловится в тике (иначе тикер Pixi, который просит
следующий кадр только после успешного обновления, встал бы навсегда). Корень
сцены ловит указатель по всему канвасу (`app.stage.hitArea = app.screen`):
тап мимо доски снимает бустер-режим, любой тап сдвигает подсказку простоя,
отпускание над пустым местом закрывает жест клетки.

- **Слои** - `core/RuntimeLayers`: контейнеры под `app.stage` в порядке
  отрисовки (`Background`, `GameBoard`, `TopMenu`, `TopMenuCenter`,
  `BottomMenu`), модули кладут себя по имени (`layers.get`). `sortableChildren`
  и у корня, и у слоёв: глубины - числа `zIndex` из `configs/sceneDepths`
  одной цепочкой (`GOAL_INTRO_OVERLAY_DEPTH` 1000 < `GOAL_PANEL_LAYER_DEPTH`
  < `GOAL_FLIGHT_DEPTH` < `CAMERA_FLASH_DEPTH`): затемнение интро, панель
  целей, полёт цели и вспышка обязаны ложиться друг на друга тем же
  порядком, а независимые литералы в разных модулях разъехались бы молча.
  Реестр слоёв живёт ровно одну партию.
- **Шина** - `core/RuntimeEvents`, типизированная карта `IRuntimeEventMap`
  (`resize`, `pause`/`resume`, `swapRequest`, `cellTap`, `swapDrag*`,
  `booster*`): опечатка в имени или чужой payload не компилируются. Своя, а
  не `EventEmitter` Pixi: чистый модуль под тестом. Обработчик, бросивший
  исключение, не роняет остальных подписчиков и того, кто эмитит, - каждый
  вызов изолирован, сбой уходит в консоль с именем события. `on` возвращает
  отписку; ядро на `destroy` снимает всех (`clear`).
- **Замок ввода** - `core/RuntimeInput`, единственный владелец
  `stage.eventMode`: включён - `static`, выключен - `none` (Pixi не ищет цели
  указателя во всём дереве). Перед каждым реальным переходом замок зовёт хуки
  сброса незавершённых жестов (`addResetHook`, регистрирует `GameLogic`);
  повторная установка того же состояния жест не обрывает.

**Уничтожение** - `GameRuntimeCore.destroy()`, идемпотентно: снять часы с
тикера и погасить все твины и задержки (`motion.destroy`: их промисы не
резолвятся - ждущие цепочки обрываются вместе с партией), `destroy()` каждого
модуля изолированно (сбой одного не останавливает остальных), замок ввода,
шина, затем `core/destroyApplication` и забыть реестр текстур. Порядок в
`destroyApplication` выверен под Pixi:

1. Сцена - **до** рендерера: `stage.removeChildren()` и
   `destroy({ children: true })` каждого ребёнка. Тексты холста на
   уничтожении отдают свои текстуры в `TexturePool`.
2. `TexturePool.clear(false)` - пул **забывается без уничтожения** текстур, до
   и после `app.destroy({ removeView: true, releaseGlobalResources: false })`:
   рендерер на своём `destroy` чистит пул уже с уничтожением, а WebGPU-батчер
   Pixi помнит эти текстуры в модульном кэше bind group-ов (см. «Известные
   ограничения») - уничтожение сыпало бы в консоль «destroyed while still
   bound» на каждый выход из партии. GPU-память уходит вместе с рендерером,
   объекты - сборщику мусора.
3. `GlobalResourceRegistry.release()` - остальные общие пулы Pixi (батчи,
   пулы холстов): живой рантайм один, делить их не с кем, а копились бы они
   от партии к партии.

Текстуры скина при этом не гаснут: файлы живут в кэше `Assets`, холсты - в
кэше `registerProceduralTextures`, обе стороны нужны следующей партии.
`bootGameRuntime().destroy` вдобавок снимает подписку на контекст и
сбрасывает `renderScale` и `sceneInsets`.

Пока играть нельзя, поверх доски крутится спиннер: до `isGameLoaded` доска
пустая. Если чанк рантайма ещё не догрузился, до самого `GameScreen`
показывается `GameLoadingShell` с тем же спиннером - второго лоадера с другим
оформлением в переходе нет. Условие (`isLoading` из `useGameRuntime`) -
`!isGameLoaded || isContextLost`: первый терм закрывает загрузку, второй -
потерянный графический контекст (см. «Загрузка ассетов и отказ рантайма»).
Сам `isGameLoaded` принадлежит одному рантайму и сбрасывается вместе с ним
(`releaseRuntime` в `useGameRuntime`): `bootGameRuntime` сбрасывает
`GameStore` уже в эффекте следующей партии, то есть кадром позже её первого
рендера, и лоадер второй партии успевал бы мигнуть на чужом флаге.

**Живой рантайм в приложении ровно один.** `GameStore`, `renderScale` и
`sceneInsets` - синглтоны на всё приложение, и две живые партии писали бы в
них наперебой. Поэтому хост обязан держать не больше одного смонтированного
экрана партии (новая партия - новый `key`, а не второй экран). Страховка -
в `bootGameRuntime`: второй рантайм гасит прошлый с `console.warn`. А
`useGameRuntime` выписывает инвариант для StrictMode: уничтожение рантайма
отложено в микротаску, а вход в эффект её отменяет, если маунт вернулся тем же
синхронным блоком.

Превью редактора - обычный `GameScreenLazy` (`widgets/levelConfigEditor/ui/
LevelConfigPreview`), а редактор - его хост, как главная: уровень, бустеры,
предуровневые бустеры, подсказки механик, зерно и `onOutOfMoves` приходят
пропсами. «+ходы» превью считает тем же правилом, что главная
(`resolveContinueOffer`), но показывает своей плашкой поверх доски
(`ui/LevelConfigPreviewContinue`), а не карточкой `outOfMoves`: модалки -
часть примера хоста, и копия шаблона, удалившая их, не должна ломать
редактор. Своего запуска рантайма у превью нет, отдельной точки входа рантайма
для редактора тоже: `bootGameRuntime` из барреля утянул бы Pixi и GSAP в
стартовый чанк каждому пользователю (см. «Бюджет бандла»).

Перезапуск превью - новый `key`, но не в том же коммите: старый экран
отпускает рантайм микротаской после cleanup (`releaseRuntime` сбрасывает
`GameStore`), и экран, смонтированный тем же коммитом, успел бы поднять свой
рантайм до этого сброса. Поэтому превью сначала размонтирует экран, а новый
монтирует следующей задачей (`setTimeout`).

`GameLogic.destroy()` первым делом ставит `isDestroyed`, снимает свои подписки
(стор near-miss, `swapRequest`, `cellTap`, `boosterStart`, `resize`, хук
сброса жеста), разбирает `SwapDragController`, `BoosterMode` (события шины,
`pointerup` корня и его отложенный таймер), подсказку и дыхание простоя,
буфер ввода, `BoardStepPlayer`, рамку выбора и эффекты доски, затем снимает
контейнер доски вместе с твинами (`destroyDisplay`). `isProcessing` при этом
поднимается навсегда: проигрывание хода могло остаться в полёте и,
дорезолвившись после выключения, не должно трогать мёртвую доску
(`BoardStepPlayer.play` проверяет `isDestroyed` перед каждым шагом,
`refreshBoardState` и финал - после каждого `await`).

### Рендерер: WebGPU и WebGL

`Application.init({ preference })` получает предпочтение из
`configs/renderer` (`resolveRendererPreference`): режим `auto` (по умолчанию)
и `webgpu` - `'webgpu'`, `webgl` - `'webgl'`. Это именно предпочтение: Pixi
пробует названный рендерер первым и откатывается на следующий, поэтому
`webgpu` в браузере без WebGPU честно даёт WebGL, а не отказ партии, а
`webgl` - единственный способ проверить WebGL-ветку на машине с WebGPU.

Режим - проп `renderer` у `GameScreenLazy` (`TRendererMode` в барреле),
кладётся в `partyOptions.renderer` до старта. Шаблонная главная берёт его из
QA-флага `?renderer=webgl|webgpu` (`shared/lib/routing/readQueryRenderer`;
другие значения игнорируются - без флага `auto`). Фактический рендерер
(`toRendererKind(renderer.name)`) лежит в `GameStore.rendererKind` и виден в
отладочной панели `?gameDebug=true` рядом с зерном, FPS и качеством. Все
эффекты сверены на обоих рендерерах; различия, которые надо помнить, - в
«Известных ограничениях».

### Пауза под карточкой результата

Паузой владеет хост: проп `paused` у `GameScreen`. Под ним
`IGameRuntime.setPaused(true)` останавливает тикер Pixi (`app.ticker.stop()`),
ставит на паузу часы рантайма (`motion.pause()`: твины, задержки,
покадровые подписчики) и шлёт `pause` в шину (звук глушит музыку);
`setPaused(false)` - обратно. Единый `IGameRuntime.setInputEnabled(false)`
закрывает замок ввода (`stage.eventMode = 'none'`), а DOM-обёртка доски
получает класс `boardLocked` (`pointer-events: none`; он же стоит, пока видна
подсказка механики). Двойная блокировка не перестраховка: слой хоста живёт в
DOM поверх доски, и при неудачном stacking context в WebView тап по канвасу
доходил бы до сцены сквозь оверлей.

Шаблонная главная передаёт `paused={useHasMountedModals()}`: признак -
«модалка в DOM», а не «модалка показана». `hideModal()` лишь снимает флаг
показа, а карточка после этого доигрывает exit-анимацию и всё это время
закрывает поле, - по признаку показа блокировка снималась бы ровно на том
кадре, ради которого заведена. Так и с «Дальше»/«Ещё раз»: новая партия
поднимается под уходящей карточкой и стоит на паузе, пока та не уйдёт.

Гасить ввод при этом обязательно, и `inert` на `#root` для этого не годится -
Pixi слушает перемещение указателя и на `document`, а слой модалок лежит
**вне** `#root`: тап по кнопке модалки иначе доходил бы до доски. Тот же ввод
гасится и пока идёт загрузка (`setInputEnabled(!paused && !isLoading)`):
спиннер поверх канваса чисто визуальный.

Переход замка закрывает незавершённые жесты (хуки `RuntimeInput.addResetHook`):
выключенный ввод отпускание пальца до клетки уже не доставит, и касание,
открывшее React-модалку, иначе оставило бы клетку «в руке». Повторная
установка того же значения идемпотентна и текущий жест не сбрасывает.

Пауза, пришедшая до готовности сцены, не теряется: рантайм её запоминает и
применяет сразу после первого отрисованного кадра (см. «Жизненный цикл
рантайма»). Ввод на старте закрыт с самого создания рантайма
(`isInputEnabledOnBoot: false`), а открывает его эффект `useGameRuntime` -
единственный владелец ввода на экране, - когда партия реально готова. Ресайз
на паузе сам рисует кадр (`app.render()`): тикер стоит, а ресайз чистит
бэкбуфер.

### Загрузка ассетов и отказ рантайма

Текстуры грузит `textures/loadSkinTextures` (`Assets.load`) по списку файлов
активного скина (`listSkinTextureFiles`). URL - Vite-импорт `?url` из папки
скина, поэтому база `VITE_CDN_BASE_URL` (-> `base` в `vite.config.ts`)
подставлена сборкой: приложение деплоится и на CDN-подпапку, и текстуры не
уходят мимо неё. Файлы грузятся по одному (`Promise.allSettled`), а не одним
`Assets.load([...])`: общий промис падает на первом битом файле и не говорит,
сколько их всего. Кэш `Assets` - по URL и на всё приложение: следующая партия
получает те же текстуры без запроса, а упавший файл из кэша выпадает и будет
запрошен заново.

Сам загрузчик стартует поздно - только после маунта экрана партии и загрузки
его чанка. Набор текстур при этом от уровня не зависит, поэтому те же файлы
греются браузером параллельно: хост зовёт `warmGameAssets()` (экспорт
`widgets/game`) в момент старта партии и не ждёт его. Список URL для прогрева
отдаёт `configs/assetsConfig.ts` (`getGameAssetImageUrls`) той же
`listSkinTextureFiles`: второй копии путей быть не должно, иначе прогрев и
реальная загрузка разойдутся. `warmGameAssets` берёт `assetsConfig`
динамическим импортом: модуль лежит в баррели виджета без Pixi (стартовый граф
хоста), а скин - отдельный ленивый чанк, общий с рантаймом партии. Прогрев
мемоизирован на запуск приложения; не загрузился даже чанк - прогрев молча
заканчивается, файлы запросит загрузчик рантайма.

Чтобы прогрев и загрузчик попали в один кэш браузера, загрузчик картинок Pixi
настроен один раз на приложение (`configureTextureLoader`): `loadTextures.config`
с `preferWorkers: false`, `preferCreateImageBitmap: false` и
`crossOrigin: 'anonymous'` - картинка грузится тегом
`<img crossOrigin="anonymous">`, как и в прогреве. По умолчанию Pixi v8 качает
картинки `fetch` в воркере и декодирует `createImageBitmap`, а такой запрос не
подхватывает ни ещё летящий img-запрос прогрева, ни его запись в кэше: на
кросс-origin CDN ответ на no-cors `<img>` для CORS-запроса непрозрачен, и
прогретые полтора мегабайта скачивались бы вторым разом. `crossOrigin` при
этом не опция, а условие: голый `<img>` с чужого origin GPU в текстуру не
пустит (`SecurityError`). Хранилищу нужны CORS-заголовки.

После загрузки картинка переводится в `ImageBitmap` (`toImageBitmap`, один
раз на приложение - источник в кэше `Assets` общий): WebGPU-рендерер Pixi не
заливает `HTMLImageElement` в GPU напрямую, а перерисовывает его в холст с
предупреждением на каждую текстуру. Битмап из уже скачанной картинки сети не
трогает и подходит обоим рендерерам; не вышло - остаётся картинка.

Спрайт-лист (файл с `frameHeight` в скине, вид клетки `frames`) режется на
кадры сразу после загрузки: `lib/sheetFrames` (`resolveSheetFrames`) даёт
прямоугольники, кадры - `Texture` с `frame` на общем источнике листа (лишней
памяти GPU не стоят). Под ключом листа в реестре - первый кадр, все кадры -
`TextureRegistry.frames(key)`. Текстуру по ключу модули берут только из
реестра (`core.textures.get`), и неизвестный ключ - исключение, а не пустая
текстура: опечатка в ключе не доживает до глаз игрока.

Затем `registerProceduralTextures` рисует процедурные холсты скина (см.
«Откуда берутся игровые текстуры»): `CanvasSource` без глобального `Cache`
Pixi. Нарисованные текстуры кэшируются **на всё приложение** (модульная
`Map`), а не гаснут с партией: рисунок статичен, а уничтоженная текстура
осталась бы висячей ссылкой в кэше bind group-ов WebGPU-батчера (см.
«Известные ограничения»).

Отказов рантайма три вида, и все уходят хосту одним колбэком `onError(reason)`
(`useGameRuntimeEvents`):

- **`assets`** - не загрузился файл скина или скелет Spine. Ключи битых
  файлов (первые пять) уходят в консоль, сцена не собирается: формально
  играбельная доска с пустыми клетками хуже честного отказа.
- **`context-lost`** - потерян графический контекст. В WebView это штатное
  событие (сворачивание приложения, нехватка видеопамяти), и Pixi
  восстанавливает его сам. `lib/watchRendererContext` подписан на оба
  рендерера: WebGL - DOM-события канваса `webglcontextlost` /
  `webglcontextrestored` (Pixi сам гасит дефолт потери и пересоздаёт ресурсы),
  WebGPU - промис `device.lost` (Pixi просит новое устройство и шлёт
  `contextChange` - это и есть восстановление; подписка на `lost`
  переставляется на каждое новое устройство). Автомат один на оба -
  `lib/contextLossGuard` (под тестом): на потерю поднимается `isContextLost`
  (экран показывает спиннер вместо чёрного канваса), на восстановление гаснет;
  не вернулся за `CONTEXT_RESTORE_TIMEOUT_MS` (15 с) -
  `failRuntime('context-lost')`. Подписка ставится сразу после `init`:
  контекст может отвалиться и во время загрузки. Тот же отказ - у init без
  единого рендерера.
- **`board`** - сорванный старт сцены. Прикрыт весь `initAnimation`, то есть
  интро цели, фон доски и `createBoard`: без любого из этих шагов партии нет.
  С тех пор как полёт цели и сборка доски идут параллельно, обе ветки ждутся
  одним `Promise.all` - пустить полёт «в воздух» нельзя: упавший твин стал бы
  unhandled rejection и не дошёл бы до `failSceneStart`, оставив
  полудостроенную сцену. Типичный случай всё же доска - `createEntityFromPiece`
  бросает на неизвестном `id` ячейки (у кода нет вида в `BOARD_VIEWS`), а
  `createBoard` обходит грид клетка за клеткой, так что исключение приходит с
  середины обхода, когда часть сущностей уже создана. Снять блокировку доски
  тут мало - играть не на чем, - поэтому `onFailure` у
  `runGuarded('initAnimation')` в `GameLogic` поднимает
  `failRuntime('board')`, а не только освобождает рантайм.

Тексты под причину лежат в виджете (`GAME_RUNTIME_FAILURE_TEXT`), а
показывает их хост: шаблонная главная возвращается в `home` и выводит причину
над кнопками.

### Часы и твины рантайма

Всё, что в партии движется или ждёт, идёт на одних часах -
`motion/RuntimeMotion` (`core.motion`), GSAP 3 под капотом:

- **Один корневой таймлайн.** Все твины и задержки рантайма - дети одного
  `gsap.timeline({ paused: true, autoRemoveChildren: true })`, поэтому пауза
  партии, ускорение темпа (`setTimeScale`) и уничтожение - по одной точке, а
  не обход всех живых твинов. Отыгравшие дети удаляются сами.
- **Часы - тикер Pixi, а не GSAP.** Корневой таймлайн стоит на паузе для
  глобального тикера GSAP, а время ему двигает `RuntimeMotion.update(deltaMs)`
  из тикера `Application` (`GameRuntimeCore.tick`): реальное время кадра,
  умноженное на темп. Остановленный тикер (пауза партии, скрытая вкладка)
  останавливает и твины, и задержки, и страховочные таймеры; тест двигает
  часы руками.
- **`tween(targets, props, options)` - промис, который нельзя потерять.**
  Самодельная обёртка
  `new Promise((resolve) => gsap.to(..., { onComplete: resolve }))`
  резолвится ровно одним способом, и его легко не дождаться:
  `killTweensOf` `onComplete` не зовёт. Наверху такой промис ждут под
  `try/finally` (обработка хода), и один потерянный конец оставлял бы
  `isProcessing` поднятым навсегда - доска замирала бы до перезагрузки.
  Поэтому промис settl'ится по трём независимым причинам: конец, остановка
  (`onInterrupt` - `kill`, `killTweensOf`) и страховочный таймер на расчётной
  длительности (`motion/tweenLifetime`, `estimateTweenLifetimeMs` + 400 мс
  запаса) - на тех же часах, что и сам твин. Если длительность не посчитать
  (`repeat: -1`), страховки нет: ложный ранний резолв рвёт цикл матчей на
  середине и хуже её отсутствия. Твин без живых целей (`null` у уничтоженной
  сущности, `HoleEntity`) не запускается и резолвится сразу. На уничтожении
  рантайма промисы не резолвятся вовсе: асинхронная цепочка обрывается там же,
  где оборвалась партия, а не доигрывает на обломках.
- **`add`** - тот же твин с ручкой `kill` (бесконечные: подсветка, пульс,
  вращение радуги). Длительность по умолчанию - 1000 мс, `yoyo` - проход
  туда и обратно на каждый повтор (`repeat: r` = `2r + 1` повторов GSAP).
  `hold`/`repeatDelay` не поддержаны.
- **`delay(ms)`** - пауза в async-цепочке, **`schedule(ms, callback)`** -
  отложенный вызов с ручкой `kill` (отложенные подписки, которые надо снимать
  на досрочном выходе: `BoosterMode` - отмена режима тапом мимо доски, таймеры
  `IdleHint`/`IdleBreathing`). Модули доски и эффекты `setTimeout` не берут:
  он переживает уничтожение рантайма, и его колбэк отработал бы по мёртвой
  доске, а задержка на часах рантайма на уничтожении просто не резолвится.
  Оконные таймеры остались только там, где часы рантайма не годятся
  намеренно: план музыки (`SoundEngine`, см. «Звук»), автомат потери
  контекста (таймер должен идти, когда тикер стоит), ожидание шрифта и
  повторный ресайз в `useGameRuntime` (рантайма ещё нет).
- **Твин объекта сцены** - `motion/displayMotion` (`addDisplayTween`,
  `tweenDisplay`): у Pixi масштаб - точка (`display.scale`), поэтому твин
  делится на два (свойства объекта и его `scale`) на одних часах с одной
  кривой, а наружу отдаётся одна ручка. `destroyDisplay` снимает твины объекта
  **до** него самого: Pixi бросает на записи в уничтоженный объект. Цепочки,
  где важен только честный конец (пульс счётчика, crossfade подписи,
  дыхание), идут через `motion.add`: у `addDisplayTween` `onComplete`
  срабатывает и на остановке.
- **`onFrame(callback, { timeScale })`** - покадровый вызов на часах рантайма
  (на паузе и после уничтожения не зовётся) для того, что интегрирует время
  само. `'follow'` (по умолчанию) - время кадра, умноженное на темп, как у
  твинов: скелеты Spine (клип клетки идёт вровень с её твинами). `'ignore'` -
  реальное время кадра: частицы, тряска и вспышка - на финале ×1.7 они не
  ускоряются, но пауза их останавливает.
- **Кривые** записываются именами, перенесёнными из Phaser-шаблона (`'Back.easeOut'`,
  `'Quad.easeIn'`) или сразу по-GSAP-овски (`'back.out'`); перевод -
  `motion/easeNames` (`toGsapEase`, под тестом): `Quad` = `power1`, `Cubic` =
  `power2`, `Quart` = `power3`, `Quint` = `power4`, семейство без
  направления - `.out`, без `ease` - линейная. Незнакомое имя с заглавной - исключение на
  первом же твине, а не тихий откат на линейную кривую.

### Шапка партии

Шапка рисуется на холсте модулями рантайма, доска видит её контрактом
`hud/boardHud` (`IBoardHud`: `init`, `decreaseMoves`, `refreshMoves`,
`refreshGoals`, `getGoalTarget`, `playIntroHold`, `playIntroOutro`) с
реализацией `hud/createBoardHud` поверх счётчика и панели целей. Состояние
партии (ходы, цели, очки) живёт в `GameStore`; шапка только показывает его и
анимирует смену.

| Модуль                                                       | Что делает                                                                                                                  |
| ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------- |
| `GameGoalsPannel` + `GoalIntro`                              | панель целей и интро (см. «Вступление партии»); пульс засчитанной цели, `getGoalTarget` - точка и масштаб иконки для полёта |
| `MovesCounter`                                               | число ходов и подпись: пульс на списании, crossfade формы слова, тревожный цвет с трёх ходов                                |
| `ScoreMeter`                                                 | полоса очков, три звезды на порогах, догон счёта (см. «Очки и звёзды»)                                                      |
| `BoostersContainer`                                          | панель `boostersBg` и подпись «Уровень N» / `title`                                                                         |
| `boosters/BoosterButton` (таблица `boosters/boosterButtons`) | кнопка бустера с остатком (см. «Кнопки бустеров»)                                                                           |
| `ExitButton`                                                 | выход по `pointerup` (`GameStore.exitButtonOnClick`)                                                                        |
| `SoundToggle`                                                | звук по `pointerup` (`writeSoundMuted`)                                                                                     |
| `IdleBreathing`                                              | дыхание фишек в покое (живёт в `GameLogic`, см. «Подсказка простоя»)                                                        |

Числа и цвета - те же дизайн-px, текстуры скина, цвета `SKIN.colors.hud` и
тексты `GAME_TEXTS`; чистые правила шапки - `lib/hudRules` (цвет ходов, места
целей, состояние кнопки бустера, звёзды, пауза дыхания).

Тексты холста создаёт только `lib/runtimeText` (`createRuntimeText`: `Text` с
якорем 0.5 по конфигу `GAME_CONFIG.*TextConfig` через чистое
`lib/runtimeTextStyle`, `resolution` = `getTextResolution()` в момент
создания). Шрифт `SKIN.fonts.game` (bold) `bootGameRuntime` ждёт до сборки
сцены (`lib/waitGameFonts`, таймаут 3 с): Pixi меряет метрики шрифта при
создании текста и сам его не перерисовывает, когда `@font-face` догрузится, -
текст, созданный раньше, остался бы запасным шрифтом до конца партии. Ошибка
или таймаут шрифта партию не роняют: сцена поднимается с запасным.

Кнопки выхода и звука срабатывают по `pointerup`, уже после того как рантайм
обработал касание: смонтируй хост на `pointerdown` свой слой поверх доски и
выключи ввод, незакрытый жест остался бы висеть.

### Spine

Вид клетки `spine` - скелет Spine вместо спрайта (`SpineCellView`, фабрика в
`CELL_VIEW_KINDS`). Контракт скина - `ISkinSpineView` (член `TSkinCellView`):
`skeleton` (URL `.json`/`.skel`), `atlas` (`url` и необязательные `pages` -
страницы атласа по имени из `.atlas` -> URL с хешем Vite), `width` - ширина
скелета, встающая на ширину текстуры покоя (масштаб `baseScale × ширина
текстуры / width`, та же дробь «дизайн-px / ширина», что у спрайта), `skin?` и
`animations` по крючкам (`idle`, `stages` - покой по прочности
`stages[hp - 1]`, `appear`, `hit`, `destroy`). Подключение в скине -
[skin.md](./skin.md#анимации-доски-и-темп).

- **Ленивость.** `spine/spineSupport` - единственная дорога к
  `@esotericsoftware/spine-pixi-v8`: `loadSpineSupport` без видов `spine` в
  активном скине возвращает `null` **без импорта** (скин по умолчанию чанк
  `spine` не качает вовсе), иначе - `import('./spineRuntime')` и загрузка всех
  скелетов до сборки сцены, параллельно с текстурами. Чанков два: `spine`
  (пакеты Spine, `manualChunks`) и маленький `spineRuntime` (обвязка); экран
  партии статически Spine не тянет - это сторожат `barrelPixiFree.test.ts` и
  `npm run bundle:check`.
- **Загрузка** - `spine/spineRuntime`: `Assets.load` скелета и атласа (импорт
  пакета регистрирует загрузчики `.atlas`/`.skel`/`.json`); страницы атласа
  из `atlas.pages` грузятся тем же путём, что файлы скина
  (`configureTextureLoader`, `toImageBitmap`). Проверяется, что все анимации
  и скин из описания есть в скелете: опечатка в имени - ошибка загрузки, то
  есть `failRuntime('assets')`, а не тихий пустой клип.
- **Время.** Скелет без своего тикера (`autoUpdate: false`): его двигает вид
  клетки с часов рантайма (`RuntimeMotion.onFrame`, `follow`) - пауза
  останавливает, ускорение доски ускоряет, как у твинов клетки. Анимации
  крючков играются на дорожке 0 (`ISpineActor.play`, промис разового прохода -
  по концу, смене анимации или снятию), остальное (переезд, масштаб нажатия,
  пульс) - твины объекта скелета.
- **Лицензия.** Spine Runtimes можно использовать, только имея лицензию Spine
  Editor (Spine Runtimes License) - она нужна тому, кто выпускает проект с
  видом клетки `spine`; пометка в README.

### Бюджет бандла

Pixi, GSAP и Spine приезжают только с ленивым экраном партии: баррель
`@/widgets/game` без них (тест-сторож `barrelPixiFree.test.ts` обходит
статический граф импортов), а `vite.config.ts` раскладывает их по своим
чанкам (`manualChunks`: `pixi` вместе с зависимостями Pixi, `gsap`, `spine`;
помощник предзагрузки Vite - в стартовый `vendor`, иначе Rollup клал его в
`pixi`, и стартовый чанк тянул весь Pixi).

Бюджет держит `npm run bundle:check` (`scripts/bundleCheck.ts`, после
`npm run build`): читает `dist/`, меряет сырой размер и gzip 9 и падает, если
чанк вышел за бюджет или нарушена ленивость движка.

| Чанк                                                                           | Бюджет, КБ (raw / gzip) |
| ------------------------------------------------------------------------------ | ----------------------- |
| старт: точка входа `index.html`, её `modulepreload` и их статическое замыкание | 500 / 155               |
| `GameScreen`                                                                   | 165 / 52                |
| `pixi`                                                                         | 645 / 188               |
| `gsap`                                                                         | 75 / 30                 |
| `spine` (необязательный)                                                       | 228 / 68                |
| `spineRuntime` (необязательный)                                                | 4 / 2                   |

Плюс две проверки ленивости: в стартовом замыкании нет ни `pixi`, ни `gsap`,
ни `spine`, а `GameScreen` не тянет `spine` статически. Бюджеты - с
небольшим запасом над текущими размерами; вырос чанк осознанно - бюджет
поднимается в скрипте с причиной в журнале [PLAN.md](./PLAN.md). В CI это
задача `bundle` в `.gitlab-ci.yml` (`npm ci`, `npm run build`,
`npm run bundle:check`, `VITE_APP_ENV=production`); выкладки ждут её, как и
`test`.

Состав стартового чанка (`index` + `vendor`, ~475 / 144 КБ): Pixi, GSAP и
Spine там нет, почти всё - React и `motion`: `react-dom` ~205 КБ, `motion`
(`motion-dom` + `framer-motion`) ~137 КБ, остальное - роутер, Zustand и код
приложения (формат и каталог уровней, главная). У исходного Phaser-шаблона
тот же старт на ~35 КБ меньше не из-за рантайма: в его lock-файле
`react-dom` 19.2.4 и `motion` 13.0.0, здесь - `react-dom` 19.3.1 (+~28 КБ
минифицированного кода) и `motion` 13.5.1 (+~6 КБ). Откатывать версии ради
размера не стали; код самого `widgets/game` в старте меньше, чем был.

### Темп доски

Все числа темпа - в `configs/timing.ts` (`DEFAULT_BOARD_TIMING`: `intro`,
`input`, `swap`, `destroy`, `fall`, `cascade`, `special`, `moves`, `idle`,
`fx`; плюс отдельный `GOAL_INTRO_TIMING` - см. «Вступление партии»). Рантайм
читает `BOARD_TIMING` - те же числа с частичным переопределением активного
скина (`ISkinManifest.timing`, слияние `lib/mergeBoardTiming` - одно, при
импорте; форма - `IBoardTiming` в `entities/skin`, расхождение с таблицей
ловит `satisfies`). Копия проекта меняет темп в `skins/<name>/timing.ts`, а не
в таблице рантайма. Разложенные по сущностям, `GameLogic` и эффектам, эти
числа позволили бы прочитать «сколько длится ход» только сложив константы из
трёх мест, а перетюнить темп - только правкой в трёх местах сразу. Форма
таблицы скопирована с `CAMERA_PUNCH`; сама `CAMERA_PUNCH` лежит в
`lib/boardFxRules` намеренно - она держит длительность в паре с силой.

То, что из этих чисел **считается**, живёт отдельно и покрыто тестами -
`lib/boardTempo.ts`:

| Правило                             | Что решает                                                          |
| ----------------------------------- | ------------------------------------------------------------------- |
| `resolveFallDurationMs(distance)`   | длительность падения растёт с расстоянием (`base + perRow × n`)     |
| `resolveFallDelayMs(stackIndex)`    | сдвиг старта соседа сверху - колонка обрушивается, а не едет плитой |
| `resolveCascadeIterationDelayMs(i)` | пауза между звеньями каскада, убывающая с глубиной, но не ниже пола |
| `resolveBoardIntroDelayMs(c,r,w,h)` | волна сборки фона доски от центра наружу (см. «Вступление партии»)  |

Характер падения задают три вещи сразу, и убрать любую значит вернуть
невесомость: кривая `Quad.easeIn` (`Back.easeOut` замедлялась к приземлению и
перелетала - физически неверно дважды), длительность от расстояния
(фиксированные 300 мс означали, что падение на пять строк идёт впятеро быстрее
падения на одну) и stagger. Stagger передаётся именно `delay` твина, а не
`motion.delay` перед ним: иначе промис резолвился бы раньше самого падения, и
анимация `settle` отпускала бы доску под ещё летящими фишками.

Падение идёт по пути из клеток, который отдаёт движок (`IBoardMove.path`, по
клетке за такт гравитации): прямые участки сливаются в одно падение с
разгоном, каждый диагональный шаг - отдельное соскальзывание под неподвижный
блокер (`lib/fallPath`, `resolveFallSegments`, с тестами). Куда лететь в
конце, `fall()` спрашивает у грида (`getVisualCoords()` по уже проставленным
`x`/`y`), а не считает от текущей позиции спрайта. В обычном ходе
это одно и то же число, но «от спрайта» любая ошибка становится вечной: догони
клетку второй проход гравитации, пока твин ещё в воздухе, - и фишка приземлится
мимо клетки навсегда, потому что новая цель отсчитается от промежуточного кадра.
`RuntimeMotion.tween` умеет резолвиться раньше честного конца (по остановке и
по страховочному таймеру - это его заявленное поведение), так что окно для
такого наложения существует. От грида кадр самоисправляется. Падение на три
строки и длиннее оставляет смаз - `IBoardFx.createFallTrail` (общий слой
частиц хвоста, с потолком живых частиц, см. «Эффекты доски»); порог и есть
весь бюджет эффекта.

Добор идёт **внахлёст** с падением, а не после него: шаг `settle` движка уже
содержит и пути падений (`moves`), и добор (`spawns` - новые фишки со своим
путём от верха колонки), а анимация шага `settle` после барьера пишет
грид спрайтов синхронно и запускает все твины разом в общий `Promise.all`.
Номер волны внутри колонки - порядок, в котором фишки трогались (снизу
вверх). Шаг `collect` («опусти вниз» на дне колонки) освобождает клетку сразу,
предмет взлетает к панели целей параллельно со следующим оседанием.

Отклонённый свап заметно короче валидного (`BOARD_TIMING.swap.rejectMs` в
каждую сторону, `Quad.easeOut` без перелёта) и заканчивается дрожью пары
(`playRejectShake`). Валидность решается **до** анимации - `BoardEngine.trySwap`
синхронный и при отказе возвращает грид как был, так что «спросить заранее» не
стоит ни кадра; иначе пара сначала ехала бы полный свап, и первая
половина промаха выглядела бы ровно как принятый ход. Тряска именно пары, а не
камеры: камера держится за наградами, чтобы неудача и успех оставались
различимы.

Появление спецфишки - собственная фаза, а не тихая запись в грид:
`spawnSpecial` (шаг `special`) даёт ей scale-in (`playSpawnPop`), белый burst и
удар `strike`. Не ожидается намеренно - спецфишка рождается в клетке фигуры,
которая в этот момент никуда не едет, поэтому выскок доигрывает поверх
осыпания доски и не добавляет к ходу ни миллисекунды. До этого иерархия была
перевёрнутой: _активация_ лазера получала полную анимацию и удар камеры, а его
_получение_ - заработанная награда - вообще ничего.

Пока в буфере ждёт ход игрока, рантайм доигрывает текущий каскад быстрее
(`PendingBoardInput.onPendingChange` -> `BOARD_TIMING.input.pendingSpeedUp`).
Темп меняется одной точкой `GameLogic.syncRuntimeTimeScale` ->
`RuntimeMotion.setTimeScale`: на часы идёт большее из темпа сцены (финал) и
ускорения буфера, поэтому буфер не перезаписывает темп финала, а после конца
партии ввод в буфер не идёт вовсе, и задержки масштабируются вместе с твинами
намеренно: на тех же часах живут и `motion.delay`, и страховочный таймер
твина - разъедься они, страховка начала бы срабатывать раньше честного конца
и рвать каскад на середине. Ускорение снимается в момент флаша
(буферизованный ход стартует уже в обычном темпе) и в `GameLogic.destroy`.
Тот же рычаг ускоряет финальный бонус (`BOARD_TIMING.finale.speedUp`).
Частицы, тряска и вспышка темпу не следуют (`onFrame` с `'ignore'`, см.
«Часы и твины рантайма»).

### Вступление партии

`GameLogic.initAnimation` - это три шага, и они идут **внахлёст**, а не в
затылок друг другу:

1. `GameGoalsPannel.playIntroHold()` - затемнение (0.8 чёрного), вход панели
   цели (`scale` 0.6 → рабочий, `Back.easeOut`) и удержание по центру. Удержания дождаться обязаны: пока
   цель по центру, показывать под ней нечего.
2. `GameGoalsPannel.playIntroOutro()` - полёт в шапку (`flyMs` 700) и снятие
   затемнения, которое начинается на `fadeStartRatio` полёта, а не после него.
3. Сборка доски - `GameBoardBackground.initGameBoard()` и `createBoard()`.

Шаги 2 и 3 запускаются вместе и ждутся одним `Promise.all`: поле собирается
**под** летящей целью, а мир открывается, пока она едет. Последовательные
«долетела → посветлело → собралась» складывались в лишние ~500 мс, за которые
на экране не происходило ничего нового. `Promise.all`, а не «полёт в воздух», -
требование `runGuarded` (см. «Загрузка ассетов и отказ рантайма»).

Интро поэтому разбито на две фазы, а состояние между ними (оверлей, финальная
позиция, флаги скипа/отпускания/уничтожения) живёт в отдельном модуле
`widgets/game/modules/GoalIntro.ts`: тап-скип и уничтожение партии обязаны
действовать в обеих фазах, а внутри
`GameGoalsPannel` эта машина состояний занимала больше места, чем сама панель.

Разделение владения простое: панель отвечает за панель и отдаёт интро ровно три
вопроса и одно уведомление (`IGoalIntroTarget` - контейнер, ширина панели, точка
прилёта из `resolveFinalPosition()`, колбэк «доиграно», по которому панель снова
начинает жить по resize). Второй копии геометрии у интро нет.
`GameGoalsPannel.playIntroHold()`/`playIntroOutro()` остаются публичными
делегатами: их зовёт `GameLogic`, и разводить эти вызовы по двум объектам
незачем. Глубину своего слоя панель поднимает сама - это её слой, а не
интро. Сами глубины - одной цепочкой в `configs/sceneDepths`: затемнение интро
< слой панели < летящая копия цели.

Прекратить интро досрочно можно двумя способами, и они не взаимозаменяемы: тап
по затемнению (`isSkipped`: доиграть мгновенно) и уничтожение модуля вместе с
партией (`GoalIntro.destroy` -> `isSceneGone`). Второй - единственный, который
обязан выйти **до** любой работы с твинами и контейнером: часы рантайма к этому
моменту уже погашены (`GameRuntimeCore.destroy`), а Pixi бросает на записи в
уничтоженный объект. Погашенные часы не резолвят и промисы удержания и полёта,
поэтому обе фазы ждут их наперегонки с собственным промисом отпускания
(`Promise.race` с `releasePromise`): `destroy` его резолвит, и фаза не висит
вечно, а продолжение `GameLogic.initAnimation` сверяется с `isDestroyed`.

Удержание - `GOAL_INTRO_TIMING.holdMs` (1 с). Прежние 2 с - это статичный чёрный
кадр и на сороковой партии подряд; по частоте показа это не «редкое событие», где
живёт бюджет на восторг.

Фон доски собирается **волной от центра наружу**: клетка прилетает
`alpha 0→1` + `scale` от `intro.tileStartScale`, `Back.easeOut`, а задержку
даёт `resolveBoardIntroDelayMs` (евклидово расстояние до центра × `waveStepMs`;
центр считается по числу клеток, поэтому на чётной стороне он лежит между
клетками). Стой `await` **внутри** двойного цикла при `duration: 5`, клетки
проявлялись бы строго по одной за кадр, и это был бы не эффект сборки, а
фрейм-лок на ~48 кадров (~800 мс). Твин - на каждую клетку со своим числовым
`delay` (у каждого своя страховка `estimateTweenLifetimeMs`), ждутся они
`Promise.all`. Клетки фона рисуются от своего центра (`anchor` 0.5 плюс
полклетки к позиции) - от угла масштабирование растило бы клетку
вправо-вниз, а не из себя.

Фишки этой волной пока не охвачены: `appearAnimation` даёт им
`scale(0)` без стаггера.

### Тайминги каскада

Урон и анимация разрушения разделены: судьбу клетки решает движок (шаг
`damage`: прочность после удара и «разрушена»), `BoardEntity.takeDamage(hp)`
только показывает её синхронно (этап блокера), а `destroy()` играет
параллельно - анимация шага `damage` синхронная, грид спрайтов освобождается
сразу, и каскад не ждёт догорания разрушений, чтобы запустить падение. Между дестроем и
падением стоит барьер `BOARD_TIMING.destroy.barrierMs`: за это время
схлопывание успевает сжать фишку, и падающая соседка не
въезжает в клетку в тот же кадр. Внутри того же барьера, а не сверх него, живёт
замах (`collapseMotion` в `cells/views/cellMotions`, `BOARD_TIMING.destroy.anticipationMs`) - удар
читается как «замах -> действие -> импакт». Отсюда инвариант таблицы:
`anticipationMs` < `barrierMs`, иначе к старту гравитации фишка стоит
увеличенной - ровно в том состоянии, ради которого барьер и заведён. Барьер не
переписывается в каждом сценарии руками: «дестрой отыграл -> доска осела» - один
шаг `settle` движка и одна его анимация (`settle` в `steps/defaultStepAnimations`: барьер +
наложенные падение и добор) на каскад, лазер и все три бустера. Корректность держится на паузе, а не
на `await` дестроя, и забытый барьер в новом бустере вернул бы ровно тот
дефект, ради которого он введён.

Прочие паузы - пауза между итерациями каскада и `BOARD_SETTLE_DELAY_MS` перед
разбором тупика; оба значения и все базовые тайминги анимаций лежат в
`configs/timing.ts` (см. [Темп доски](#темп-доски)).

Учёт целей при этом не откладывается: проигрыватель шагов засчитывает цели
шага до его проигрывания (`registerGoals`) и сразу перерисовывает панель - за
шаг, а не за клетку, - анимация дестроя на это не влияет.

Неожидаемый дестрой запускается не голым `void`: `takeDamage()` зовёт
`BoardEntity.runDestroy()`, то есть тот же `runGuarded`, что и остальные
асинхронные сценарии из синхронных колбэков рантайма - иначе падение внутри
`destroy()` на уничтожаемой партии становилось бы unhandled rejection без
имени сценария в консоли.

### Кнопки бустеров

Все три кнопки нижней панели - один класс `modules/boosters/BoosterButton.ts` с
конфигом; сами конфиги (вид, текстура, смещение `offsetX`) лежат таблицей
в `modules/boosters/boosterButtons.ts`: три класса, отличающиеся четырьмя
строками, разъезжались бы - вроде проверки занятости доски до проверки
остатка у одной кнопки и после - у другой.

Тап кнопки - на `pointerdown`: кнопка эмитит в шину `boosterStart` с видом
бустера, а режим выбора цели ведёт `modules/BoosterMode`. Отмену режима тапом
мимо доски ловит `pointerup` корня сцены, и `BoosterMode` подписывается на
него с задержкой 300 мс на часах рантайма (`motion.schedule`) - именно чтобы
отпускание того же нажатия до него не дошло. Клетка-цель гасит всплытие
своего `pointerup` (`event.stopPropagation()` в
`CellInputController.onBoosterUp`): иначе отпускание дошло бы до корня, и
режим принял бы его за тап мимо доски. Повторное нажатие кнопки режим снимает.

Кнопка про игровую логику знает ровно одно - занята ли доска (зеркало
`GameStore.isBoardBusy`); режим бустера включает `GameLogic` в ответ на
`boosterStart`, а о конце режима и остатке кнопка узнаёт событиями
`boosterEnd` и `boosterInventoryChanged`. Включение режима не только
переводит клетки в режим цели, но и запирает жест хода - см. «Ввод: слежение
за пальцем, коммит на отпускании».

Бустеры бывают скрыты (панель не видна, кнопки не видны и не кликаются) -
это правило рантайма, собранное в одном хелпере `areBoostersHiddenForParty()`
(`widgets/game/model/areBoostersHiddenForParty`): партия начата с пустым
списком бустеров. Какие партии идут без бустеров, решает хост (шаблонная
главная - первый уровень, `resolvePartyBoosters`); список кладётся в
`levelConfigStore` до старта рантайма и внутри партии не меняется, поэтому
модули читают правило один раз. Читают его `BoostersContainer` (видимость
самой панели `boostersBg`) и `BoosterButton` (видимость кнопки со счётчиком,
интерактивность, гварды тапа и `syncState`); превью редактора уровней
передаёт `DEFAULT_LEVEL_BOOSTERS` и бустеры не теряет.

Прячется именно панель бустеров и кнопки, а не весь нижний контейнер: в нём же
лежит подпись «Уровень N» - к бустерам она отношения не имеет, и первый уровень
остался бы без неё.

Раскладка бустеров (`initBoosters`) всегда держит все три вида
(`GAME_BOOSTER_KINDS`), не выданный партией бустер заводится с нулевым остатком.
Бустер описывается одним видом (`ball`/`laser`/`beam`) и остатком
(`IGameStartBooster`), без серверных кодов и числовых типов.

Видимостью, а не альфой: альфой кнопки уже владеет `syncState` (притушенная
0.35 при нулевом остатке), и два владельца одного свойства разъехались бы.

### Ошибки в асинхронных сценариях

Шина рантайма, обработчики указателя Pixi и тикер не ждут промис обработчика
и не ловят его ошибку, поэтому каждая входная точка асинхронного сценария
обёрнута в `widgets/game/lib/runGuarded.ts`: подписка синхронная, а тело
живёт в `runXxx`-методе. Обёртка логирует сбой с именем сценария (и
синхронное исключение до первого `await` тоже) и отдаёт вызывающему
`onFailure` - снять блокировку доски (`releaseBoard`). Без неё исключение
внутри цикла матчей становилось бы unhandled rejection и оставляло бы
`isProcessing` поднятым - партия замирала бы без единого следа в консоли.

**Сценарий может пережить свою партию.** Интро цели на уничтожении намеренно
отпускает ожидание (`GoalIntro.destroy` резолвит промис отпускания), поэтому
продолжение `GameLogic.initAnimation` выполняется уже после
`GameLogic.destroy()`: игрок закрыл партию посреди интро, исход пришёл из
отладочной кнопки, редактор перезапустил превью. Ядро передано явно, и до
ядра следующей партии старый модуль не дотянется, но `GameStore` - синглтон и
к этому моменту принадлежит уже новой партии. Отсюда два правила `GameLogic`:

- `destroy()` первым делом ставит `isDestroyed`, и асинхронный сценарий
  проверяет его после каждого `await`, прежде чем трогать сцену или стор;
- аварийные выходы (`releaseBoard`, `failSceneStart`) на уничтоженной доске в
  стор не пишут, и `destroy()` поднимает `isProcessing` полем, без зеркала в
  стор. Без этого сбой старого рантайма (`failRuntime('board')`) ронял бы
  следующую партию на главную, а превью - в панель отказа.

Тексты причин лежат отдельным правилом
`widgets/game/model/gameRuntimeFailureText.ts`, а не внутри хука: читателей два.
Второй - превью редактора уровней: оно получает отказ тем же `onError` и
рисует панель с заголовком причины вместо доски (описание там для игрока).
Редактор - единственное место, где уровень собирают руками, и сорванный старт
сцены тут самое ожидаемое событие.

### Движок доски

Правила доски живут в чистом движке `BoardEngine`
(`src/entities/game/engine`), без рантайма отрисовки. Класс - фасад публичного API, а
правила - модули над общим состоянием доски (`boardState`: слои, паспорта,
случайность партии): урон по слоям - `boardDamage`, спецфишки и комбинации -
`boardDetonation`, оседание, добор и каскад - `boardCascade`, слизь -
`boardSlime`, поиск и оценка ходов - `boardMoves`. Порядок обращений к
случайности и выдачи паспортов - часть контракта: та же партия с тем же
зерном повторяется до клетки. Движок держит свой грид
(`grid[col][row]`) с фишками (`TBoardPiece`: `id` - код клетки, `uid` - паспорт
фишки на всю партию, `hp`), разыгрывает ход целиком и синхронно - свап, все
звенья каскада с фигурами, взрывы спецфишек и комбинации, урон, гравитацию,
добор, бустеры, перемешку тупика - и возвращает протокол шагов (`TBoardStep`):

| Шаг                                 | Что показывает рантайм                                                                          |
| ----------------------------------- | ----------------------------------------------------------------------------------------------- |
| `swap`                              | пара меняется клетками (`playSwapStep`)                                                         |
| `detonate`                          | взрыв спецфишки или комбинации до урона (`TBoardBlast`; вид взрыва - реестр `BLAST_ANIMATIONS`) |
| `transform`                         | фишки превращаются в спецфишки (радуга+спецфишка)                                               |
| `beam` / `colorSweep` / `rowsBlast` | анимация бустера до урона                                                                       |
| `damage`                            | пачка ударов по слоям: предмет, накладка или подложка                                           |
| `matches`                           | звено каскада: «×N», хайп-фраза, удар камеры                                                    |
| `special`                           | родилась спецфишка за фигуру                                                                    |
| `settle`                            | барьер, пути падений и добор внахлёст (`settle`)                                                |
| `collect`                           | «опусти вниз» собраны на дне колонки                                                            |
| `cascadePause`                      | пауза перед следующим звеном                                                                    |
| `shuffle`                           | перемешка тупика                                                                                |

Шаги проигрывает `modules/BoardStepPlayer` по порядку (`play`) и ничего не
решает сам: что разрушить, куда упасть и какого цвета добор, движок уже
записал в шаг. Он же держит зеркало доски спрайтами: пока шаги играют, движок
стоит в конце хода, а спрайтовый грид догоняет его шаг за шагом; на свободной
доске они совпадают клетка в клетку - в dev это проверяет `assertInSync` на
каждом освобождении доски. Акценты звена каскада (`matches`) - отдельный
`modules/CascadeAccents`.

`GameLogic` остаётся оркестратором хода: жест, занятость доски
(`setProcessing`), списание хода и заряда, тупик, исход и финал. Буфер ввода
под каскадом - `modules/PendingBoardInput`, выбор первого тапа и рамка над
ним - `modules/SelectionMarker`. Спрайт уходит с доски одним путём
`BoardStepPlayer.detach` (удар, превращение, сбор, слизь, предбустер),
а центр клетки в дизайн-координатах у всех один - `lib/boardGeometry`. Выбор цели
бустера - `modules/BoosterMode`: кнопки включают режим, тап по клетке отдаёт
её `GameLogic`, тап мимо доски или повторное нажатие режим снимают. Заряд
списывается только после `BoardEngine.canApplyBooster`: неприменимый бустер
(дыра, «лазер» по блокеру) снимает режим, заряд остаётся у игрока.

Проигрывание, оборванное уничтожением партии, тихо выходит, а `refreshBoardState`
и финал сверяются с `isDestroyed`: стор к этому моменту принадлежит следующему
рантайму, и исход мёртвой доски записался бы новой партии.

API движка: `BoardEngine.fromLevel(grid, { colors, random, isPriorityTarget })`,
`trySwap(from, to)` (`blocked` / `rejected` / `accepted` с шагами),
`activateSpecialAt(cell)`, `canApplyBooster(kind, cell)`,
`applyBooster(kind, cell)` (`null` - бустер к клетке неприменим),
`resolveDeadEnd()` (`hasMove` / `specialHint` / `shuffled` / `stuck`),
`findHint()`, `hasMove()`, `pieceAt()` (только чтение), `locate(uid)`. Конструктор из готовых
фишек (`new BoardEngine(seeds, ...)`) нужен тестам, реплеям и будущему боту.

Чего движок не знает: ходов, целей и исхода - их ведёт `GameStore` по шагам
хода (`listGoalEvents` в `BoardStepPlayer`), а также анимаций и времени. Единственное, о чём движок спрашивает рантайм, - приоритетная цель
пропеллера (`isPriorityTarget`: то, что ещё нужно цели уровня); стор
опрашивается в момент полёта. Случайность - только переданная (`random`): добор берёт цвета уровня
(`IMinigameLevelConfig.colors`), перемешка - перестановки, и всё это от зерна
партии (`createSeededRandom(seed)`, `shared/lib/random`). Зерно приходит
пропом `seed` (у хоста - QA-флаг `?seed=N`), без него - случайное; текущее
видно в отладочной панели (`?gameDebug=true`). С тем же зерном и теми же
ходами партия повторяется до клетки. Косметика (дыхание фишек) берёт
`Math.random`, чтобы не сдвигать последовательность движка.

Блокер, задетый одним событием дважды (соседний с двумя гаснущими фишками, на
луче и рядом с ним), получает один удар - «за событие», а не за всю цепочку:
держи это правило общий для всей цепочки лазеров список задетых, второй лазер
цепочки мимо уже задетого первым ящика проходил бы без удара.

### Спецфишки и комбинации

Фигуру и её награду определяет чистое правило `entities/game/lib/boardShapes`
(`findBoardShapes`). Линии из 3+ и квадраты 2×2 одного цвета, делящие клетку,
считаются одной фигурой, а её вид выбирается по приоритету жанра:
5 > L/T > 4 > 2×2 > 3. Квадрат 2×2 - полноценная комбинация во всех правилах:
в `findBoardMatches` (`squares`), в «есть ли ход», в подсказке простоя, в
генераторе редактора (он не ставит готовых квадратов) и в перемешке.

| Фигура  | Спецфишка | Спрайт                          | Эффект                                        |
| ------- | --------- | ------------------------------- | --------------------------------------------- |
| 4 в ряд | ракета    | `LaserEntity` (`rocket`)        | строка или колонка (ось четвёрки)             |
| 2×2     | пропеллер | `PropellerEntity` (`propeller`) | крест вокруг себя + полёт в приоритетную цель |
| L/T     | бомба     | `BombEntity` (`bomb`)           | квадрат 3×3                                   |
| 5 в ряд | радуга    | `RainbowEntity`                 | все фишки цвета партнёра по свапу             |

Спецфишка рождается в клетке свапа (если та в фигуре), у L/T иначе - на
пересечении, в каскаде - в клетке самой нижней только что упавшей фишки
фигуры, иначе - в её средней клетке (`BoardEngine.planSpecial`). Клетка свапа
действует только в первом звене каскада. Своего арта у радуги нет: её
текстура - цветовое колесо из цветов фишек, процедурная `rainbowWheel`
скина (`skins/default/art/boardArt`).

Срабатывает спецфишка тремя путями: свапом с любым соседом (радуга - по цвету
партнёра), одиночным тапом (радуга - по самому частому цвету; тап - это ход и
списывает его, см. «Ход двумя тапами») и под чужим эффектом. Задетая взрывом или бустером спецфишка не гаснет, а взрывается сама -
**на месте и сразу**, до оседания: вся цепочка играет одним залпом
(`strike` -> `detonate` в движке, `IChain` следит, чтобы каждая сработала
один раз), и только потом доска осыпается.

Комбинации - свап двух спецфишек, в клетке, куда игрок довёл свою:

| Пара                     | Эффект                                                              |
| ------------------------ | ------------------------------------------------------------------- |
| ракета + ракета          | крест: строка и колонка                                             |
| ракета + бомба           | по три строки и колонки                                             |
| бомба + бомба            | квадрат 5×5                                                         |
| радуга + ракета/бомба    | фишки самого частого цвета становятся спецфишкой пары и срабатывают |
| радуга + пропеллер       | то же - фишки цвета становятся пропеллерами и улетают               |
| радуга + радуга          | удар по всему полю                                                  |
| пропеллер + ракета/бомба | пропеллер несёт её к цели, там она срабатывает                      |
| пропеллер + пропеллер    | крест и три полёта к разным целям                                   |

Цель пропеллера: сначала то, что нужно цели уровня (`isPriorityTarget`),
затем блокеры, затем фишки; спецфишка - только если больше лететь не во что.
Внутри яруса - случайно, от зерна партии. Бустеры бьют той же системой урона:
луч по спецфишке её взрывает.

Анимации взрывов - `fx/specialFx` (лучи ракеты `playBeamSequence`, ударная
волна бомбы, взлёт и полёт пропеллера дугой с хвостом, лучи радуги); темп -
`BOARD_TIMING.special`, длительность полёта от расстояния -
`resolvePropellerFlightMs` в `lib/boardTempo`.

Бустер «шар» бьёт три строки вокруг выбранной клетки (у края поля - две), и
шаг `rowsBlast` несёт их списком: `row` - строка шара, `rows` - все задетые.
Анимация - `fx/boosterFx` (`playRowsWave`): волна на каждой строке из `rows`
вровень и шар с хвостом по своей строке. Она не привязана к спрайту клетки:
средняя строка может быть сплошь из дыр, а волна всё равно должна пройти.
Шар улетает за правый край сцены, переведённый в координаты контейнера доски
(`container.toLocal`): контейнер сдвинут и отмасштабирован экраном и ужатием
крупного поля, и голая ширина сцены сделала бы скорость пролёта зависимой от
экрана и размера поля. Волны раскрываются из-под маски-полосы на контейнере
волн.

### Слои клетки и препятствия

Клетка доски - три слоя (формат уровня v2, см. [levels.md](./levels.md#клетка---слоями)):
накладка (`overlays`), предмет (`grid`) и подложка (`floors`) - у движка это
три сетки, у каждого объекта свой паспорт. Накладки и подложки статичны,
поэтому лежат по клеткам, а не едут с фишками.

Урон приходит событием (`strike`/`damageCells`) прямым ударом (матч на
клетке, взрыв по ней, бустер) или брызгом (матч рядом, соседи линии ракеты и
целей радуги). По клетке он идёт сверху вниз:

- накладка принимает удар на себя: лёд - любой, цепь - только прямой;
  фишка под ней не страдает;
- иначе предмет: фишка и спецфишка - прямой (спецфишка не гаснет, а
  взрывается), ящик и слизь - любой, камень - только прямой (то есть от
  спецфишек и бустеров: в матч камень не попадает), «опусти вниз» - никакой;
- если прямой удар погасил предмет (или клетка была пуста) - слой подложки.

Удар записывается с паспортом, кодом и слоем (`IBoardHit.id/layer`), и
рантайм бьёт нужный спрайт: предметы - `BoardEntity` (`CargoEntity` листает
стадии сталь -> целый -> треснувший - текстуры и тинт стадий из скина,
`StoneEntity`, `SlimeEntity`, `DropEntity`), накладки и подложки - `cells/LayerEntity` в своих слоях
контейнера доски. По коду удара прогресс целей и очки считают чистые правила
(`boardProgress`, `boardScore`) - для бота, которому спрайты не нужны.

Слизь расползается после хода игрока (свап или тап по спецфишке), который не
снял ни одной её клетки: `BoardEngine.spreadSlime` выбирает случайную слизь и
соседнюю свободную фишку (не под накладкой и не спецфишку) и пишет шаг
`spread`. Рантайм тихо убирает поглощённую фишку (`BoardEntity.vanish` - не в
цель и без частиц) и выращивает слизь из соседней клетки
(`SlimeEntity.playSpread`). Бустер ходом не считается и слизь не будит.

Правила линий видят слои: фишка подо льдом в линию не идёт (`matchView`),
фишка под любой накладкой не свапается и не падает (клетка `fixed` для
гравитации), спецфишка за фигуру не рождается в клетке под накладкой (там
фишка матчем не гаснет). Перемешка трогает только свободные фишки. Радуга
бьёт и фишки своего цвета под накладками (удар примет накладка), а
превращает (радуга+спецфишка) только свободные.

«Опусти вниз» собирается, когда стоит на дне своей колонки (ниже только
дыры): после каждого прохода гравитации движок снимает такие предметы
(шаг `collect`) и роняет доску ещё раз. Ящик под ним держит предмет, пока
не разбит.

Цель пропеллера движок выбирает по слоям клетки: `isPriorityTarget` получает
коды всех слоёв (`['chain', 'red', 'floor']`), и рантайм отвечает, нужен ли
какой-то из них цели уровня.

### Чистые правила доски

Правила, которым рантайм отрисовки не нужен, живут отдельными функциями в домене и
покрыты тестами; движок собирает из них ход:

| Правило                                           | Файл                                     | Что решает                                         |
| ------------------------------------------------- | ---------------------------------------- | -------------------------------------------------- |
| `findBoardMatches` / `hasBoardMatch`              | `entities/game/lib/boardMatches.ts`      | все комбинации на доске (линии и квадраты 2×2)     |
| `findBoardShapes`                                 | `entities/game/lib/boardShapes.ts`       | фигуры и их вид: 5 > L/T > 4 > 2×2 > 3             |
| `hasPossibleMove`                                 | `entities/game/lib/boardMatches.ts`      | есть ли ход - свап пары соседей, дающий комбинацию |
| `findHintMove`                                    | `entities/game/lib/findHintMove.ts`      | первый ход от центра наружу (лучший - движок)      |
| `resolveRandomCells`                              | `entities/game/lib/randomCells.ts`       | цвета клеток «?» без готовой фигуры                |
| `countGoalProgress`                               | `entities/game/lib/boardProgress.ts`     | прогресс целей по шагам хода (бот, тесты)          |
| `scoreBoardSteps`                                 | `entities/game/lib/boardScore.ts`        | очки по шагам хода                                 |
| `resolveLevelStars`                               | `entities/game/lib/levelStars.ts`        | звёзды партии (`null` - у уровня звёзд нет)        |
| `listLevelMechanics`                              | `entities/game/lib/levelMechanics.ts`    | механики уровня для обучения                       |
| `planBoardGravity`                                | `entities/game/lib/boardGravity.ts`      | дыры, неподвижные, диагональ, добор на месте       |
| `planShuffledLayout` / `planGuaranteedMoveLayout` | `entities/game/lib/reshuffleLayout.ts`   | раскладка перемешивания                            |
| `generateMinigameLevelGrid`                       | `entities/game/lib/minigameLevelGrid.ts` | случайное поле под цели уровня для редактора       |

Гравитация, перемешка и подсказка живут рядом с `boardMatches`, а не в
`widgets/game/lib`: движку в домене импортировать из виджета нельзя. Генератор поля обещает три вещи и проверяет их тестами: размер
поля сохраняется, стартовых комбинаций нет (рантайм их не разбирает -
`createBoard` собирает доску и сразу отдаёт ход), ход на поле есть, если он там
возможен. Плюс учитывает цели и цвета уровня: блокеры кладутся в количестве
`goal.count` - сами они не выпадают, а фишки цвета цели достаточно засеять
тройкой, потому что движок досыпает цвета уровня равномерно.

Клетка для правил - это что угодно с полем `id`, а «участвует ли клетка в
матче» приходит предикатом (`isChipPiece` у движка). Поэтому тест подаёт
правилу обычные объекты и раскладывает доску строками, как её видит игрок.

Два следствия, за которые правила и вынесли:

- обход горизонтали и вертикали в `findBoardMatches` - одна функция с колбэком
  направления: две почти одинаковые копии разъезжаются - вплоть до
  перепутанных в результате осей, которые пришлось бы компенсировать
  перестановкой полей на стороне вызывающего;
- `hasPossibleMove` перебирает свапы по собственной копии колонок: свап прямо
  в живом `_grid` с возвратом клеток обратно при выходе из середины перебора
  оставил бы доску перевёрнутой.

Гравитация (`planBoardGravity`) идёт тактами: за такт фишка сдвигается не
больше чем на клетку. Клетка для правила - `open` (фишка или пусто), `hole`
(фишка пролетает насквозь, но не встаёт - поведение исходной гравитации,
перенесённое один в один) или `fixed` (ящик, камень, фишка под накладкой -
сквозь неё не падают). Фишка падает прямо вниз; если снизу занято или
неподвижно, соскальзывает по диагонали - но только в клетку, куда сверху
ничего не придёт (над ней неподвижная). Новые фишки встают в верхнюю
открытую клетку колонки. Когда падать больше некому, оставшаяся пустая
клетка недостижима (верх под серединой ряда неподвижных шириной от трёх,
замкнутый карман) - движок добирает её на месте: спавн шага `settle` с
`inPlace: true` и путём из одной этой клетки. Проигрыватель
(анимация шага `settle`) не везёт такую фишку сверху сквозь блокер, а
выращивает её в клетке (`appearAnimation`, как на старте партии).
Если «фишка не должна проходить дыру» - это продуктовое решение, и менять
его надо в правиле вместе с тестом.

### Перемешивание доски

Тупик (ходов фишками нет и спецфишки на доске нет) разбирает
`BoardEngine.resolveDeadEnd`. Раскладка описывается перестановкой «фишка ->
клетка» над двумя списками одинаковой длины
(`entities/game/lib/reshuffleLayout.ts`), поэтому фишка не может потеряться:
при сканировании грида фишка ложилась бы, только если клетка «выглядит
свободной», а не поместившиеся выпадали бы из грида, оставаясь живыми
спрайтами на экране. Блокеры и дырки при этом не трогаются вовсе - их клетки в
перестановку не входят.

Проверка идёт по синхронно применённой раскладке, а анимация - один раз в
конце (шаг `shuffle`): иначе каждая неудачная попытка проигрывала бы полсекунды
тряски, и десять попыток подряд превращались бы в пять секунд ожидания.

Вероятностный цикл (`RESHUFFLE_ATTEMPTS`) не сдаётся молча. Если ход так
и не появился, раскладку строит детерминированное правило
`planGuaranteedMoveLayout`: две фишки одного цвета в линию по `x`, третья -
«крючком» сбоку от дальней клетки линии, так что свап всегда достраивает три в
ряд. Если и его построить нельзя (мало свободных клеток, ни одного цвета в трёх
экземплярах), ходов на доске не существует в принципе - движок возвращает
`stuck`, и партия завершается поражением. Без этого исхода игрок оставался бы
на неиграбельной доске: ни победы, ни поражения, ходы не тратятся.

## Store actions

Набор кнопок результата - чистое `resolveGameResultActions(resultKey)`
(`src/widgets/modals/model/resolveGameResultActions.ts`: победа -
«Дальше»/«На главную», поражение - «Ещё раз»/«На главную»). Что делает каждая
кнопка, решает хост: обработчики `onPlay`/`onHome` приходят пропсами модалки
(`IGameResultModalProps`), а `useGameResultActions` закрывает карточку и зовёт
обработчик тем же React-коммитом. Набор кнопок приходит из хука готовым
списком (`actions`), а не собирается ветвлением в `ModalVictory`/`ModalDefeat`.
Закрытие без выбора (Escape) - то же, что «На главную»: под карточкой доски уже
нет. Клик мимо карточки результата её не закрывает (`closeOnOverlayClick={false}`).

`victory` и `defeat` объявлены в `src/widgets/modals/model/modal-registry.ts`
как `base` с `priority: 2` и `closeOnRouteChange`, рядом - `levelStart`
(карточка уровня, `priority: 2`) и `outOfMoves` (near-miss, `priority: 1`: исхода
ещё нет, и она важнее карточек результата). Хост закрывает все четыре
(`hideMany`) на каждом старте, выходе и отказе. «Дальше» и «Ещё раз» на
карточке результата открывают карточку уровня, а не партию сразу.

## Известные ограничения

- **Кэш bind group-ов батчера Pixi растёт за сессию.** `getTextureBatchBindGroup`
  (`pixi.js`, `lib/rendering/batcher/gpu/getTextureBatchBindGroup.mjs`, Pixi
  8.22) кладёт `BindGroup` каждой новой комбинации текстур батча в модульный
  объект `cachedGroups` по хешу `uid` текстур и никогда его не чистит. Зовут
  его WebGPU-батчер спрайтов (`GpuBatchAdaptor`, `GpuGraphicsAdaptor`) и общий
  для обоих рендереров `GraphicsContextSystem` (небатчевые `Graphics`), то есть
  на WebGPU кэш пополняется каждой новой комбинацией текстур в батче, на
  WebGL - заметно реже. Каждая запись подписана на `change` своих
  `TextureSource`/`TextureStyle` и держит на них ссылку: источники, попавшие в
  кэш, сборщику мусора не уходят, а уничтоженный источник даёт в консоль
  «[BindGroup] ... destroyed while still bound». Публичного способа очистить
  или ограничить кэш у Pixi нет: `getTextureBatchBindGroup` экспортирован, а
  `cachedGroups` - нет; в `GlobalResourceRegistry` он не зарегистрирован
  (`release()` чистит пул батчей, `TexturePool`, `CanvasPool`, `BigPool`, кэш
  холстов, но не его), рендерер на `destroy` его не трогает, а `destroy()`
  полученного из него `BindGroup` оставил бы в кэше сломанную запись, которую
  батчер выдаст снова. Что сделано, чтобы рост был ограниченным и тихим:
  - текстуры живут на всё приложение и от партии к партии не меняются -
    файлы скина в кэше `Assets`, процедурные холсты в кэше
    `registerProceduralTextures`, кадры спрайт-листов делят источник листа:
    повторная партия переиспользует те же `uid` и те же записи кэша;
  - `destroyApplication` забывает `TexturePool` без уничтожения
    (`TexturePool.clear(false)`): текстуры текстов холста не гаснут под живыми
    записями кэша, поэтому предупреждений нет (растут только эти записи - по
    новым текстурам текстов каждой партии);
  - `?renderer=webgl` (проп `renderer="webgl"`) - запасной путь, если рост на
    конкретном устройстве окажется заметным: спрайты на WebGL этот кэш не
    пополняют.
    Насколько вырастает кэш за длинную сессию на реальном устройстве, не мерили;
    настоящее лечение - в самом Pixi (очистка кэша на уничтожении рендерера или
    слабые ссылки).
- **Темп на ~3-5% быстрее Phaser-шаблона при тех же числах `BOARD_TIMING`.**
  Phaser квантовал каждый твин и задержку по кадру и стартовал твин со
  следующего кадра, GSAP на часах рантайма - нет. Порядок и длительности те
  же, события `onBoardEvent` и исход при том же зерне совпадают.
- **Интро по стенным часам на ~200 мс длиннее, чем по часам рантайма**:
  кадр сразу после старта долгий (React снимает спиннер, текстуры уходят в
  GPU), а тикер Pixi такой кадр во время партии не засчитывает.
- **Spine.** У вида `spine` нет украшений покоя (`ICellLook.decorate`:
  поворот ракеты, вращение радуги) - скелет анимирует себя сам; центр клетки -
  центр рамки позы покоя, а не корень скелета. Скелет и `.atlas` качаются
  `fetch` - на CDN другого origin нужны CORS-заголовки. В шаблоне нет ни
  одного скелета: контракт проверен тестами и изолированной сценой, а не в
  настоящей партии.
- **Мелкие отличия от Phaser-шаблона**: подъём глубины нажатой клетки не
  перенесён (у Phaser в контейнере он и не работал); пульс счётчика ходов -
  две половины (`Quad.easeOut` вверх, `Quad.easeIn` вниз) вместо yoyo с
  колбэком середины; хвост полёта гаснет с последней частицей, а не по
  таймеру; частица рождается в свой первый кадр в точке рождения.
- **Скрытая вкладка или скрытая панель превью** душит `requestAnimationFrame`:
  FPS там 0-2, перф-гейт и анимации так не проверить - смотреть на видимой
  вкладке.

## Открытые вопросы

- **Производительность на слабом устройстве не замерена на живом
  телефоне.** Автоматика и инструменты есть (см. «Перф-гейт»: понижение
  качества на просадке, FPS в отладочной панели, `?perf=low`, бюджет скорости
  движка), но ручной гейт на бюджетном Android - медиана FPS во время каскадов
  на уровне 29 - перед релизом ещё предстоит, на обоих рендерерах. Это
  гейт и для любых новых эффектов.

### Откуда берутся игровые текстуры

Текстуры, их ширины, цвета холста, шрифт текстов холста и звуки - часть
скина (`src/entities/skin`, папка `skins/<name>/`; подробно -
[skin.md](./skin.md)). Текстур два источника, и потребителю (сущности,
модулю, эффекту) всё равно, какой: он берёт текстуру по ключу.

- **Файлы** — `textures.files` скина: в скине по умолчанию это
  `skins/default/images/*.webp`, Vite-импорт `?url` в `textures.ts`. Грузит их
  `loadSkinTextures`, прогревает `warmGameAssets` (через `assetsConfig`) - оба
  по `listSkinTextureFiles`, один URL на обоих (см. «Загрузка ассетов и отказ
  рантайма»). Это фишки шести цветов
  (`chip_*`), спецфишки (`rocket`, `bomb`, `propeller`) и блокеры
  (`cargo`/`cargo2`, `stone`, `ice`/`ice2`, `chain`); `hole.webp` - только
  иконка DOM. Кадры вырезаны из атласов по их JSON-таблицам и подняты с 100 до
  `CELL_TEXTURE_WIDTH` (168 px, у цепи 168×171) с Lanczos-фильтром: так все
  они живут на общем `BASE_SCALE`, а повышение разрешения офлайн чище, чем
  растяжение на GPU.
- **Процедурные** — `textures.art` скина: рисование Canvas 2D
  (`skins/default/art`), регистрирует его `widgets/game/textures`
  (`registerProceduralTextures` из `bootGameRuntime`, после загрузки файлов,
  кэш на всё приложение) под
  своими ключами. Это клетки поля (`tile`, `tileBright`), слизь, кристалл
  «опусти вниз» (`drop`), подложка (`floor`, `floor2`) и колесо радуги
  (`rainbowWheel`) — `boardArt`; панели целей и бустеров, плашки шапки, кнопка
  звука (`soundToggleOn`/`soundToggleOff`), подсветка и иконки бустеров
  (`boosterBeam`/`boosterLaser`/`boosterBall`) — `hudArt`; кадры луча ракеты
  (`laser1`..`laser9`, число - `ROCKET_BEAM_FRAME_COUNT`), луч и кольца
  бустера «луч» (`light`, `ellipse`), звезда бустера «лазер» (`portal`), волна
  бустера «шар» (`wave`) и частица (`particle`) — `fxArt`. Других путей
  рисовать текстуру в рантайме нет: сущность или модуль не генерирует её сам
  при первом `render()`. Цвета рисования - `skins/default/palette.ts`.

**Файл важнее холста**: ключ, загруженный файлом, `registerProceduralTextures`
пропускает - так скин заменяет любую процедурную текстуру картинкой, не трогая
код рисования. Ключи, которые рантайм берёт по имени, - `RUNTIME_TEXTURE_KEYS`;
ключи текстур элементов скин называет сам в описании элемента
(`board.texture`, `board.stages`). Что каждый нужный ключ есть, что в скине нет
лишних файлов, что текстуры элементов ширины `cellWidth` и что холст уступает
файлу - держат `entities/skin/model/registry.test.ts` и
`widgets/game/textures/proceduralTextures.test.ts`.

Исходные атласы, из которых нарезаны кадры, в репозиторий не входят
(`assets-for-new-match3/` в `.gitignore`): это чужой арт, права на который не
подтверждены. Перед выпуском продукта на шаблоне кадры атласов нужно
заменить на арт с подходящей лицензией - заменой папки скина.

DOM процедурных текстур не видит, поэтому у того, что показывается вне
канваса, иконка - своя в папке скина (`icons/`): `random` («?»), `slime`,
`drop`, `floor` и `rainbow` (палитра редактора, цели на карточках, подсказки
механик, карточка уровня). Рисуя новую процедурную текстуру, нужную и DOM,
держите двойник в той же геометрии.

Фишки разрушаются без покадровой секвенции: замах, вспышка частиц и
схлопывание (`collapseMotion`, `BOARD_TIMING.destroy.collapseMs`). Ракета при
выстреле вспыхивает тинтом (`LaserEntity`, `SKIN.colors.fx.rocketFiring`) —
отдельной «активной» текстуры у неё нет. Покадровое разрушение даёт вид
клетки `frames` из скина (см. [skin.md](./skin.md#анимации-доски-и-темп)).

### Размеры игровых текстур

Правило одно: **ширина исходника = дизайн-px × 4** (с историческим
знаменателем `CELL_TEXTURE_WIDTH = 168` под клетку в 42 дизайн-px; в скине -
`metrics.ts`, в манифесте - `textures.cellWidth`). Масштаб записывается
**дробью «дизайн-px / ширина текстуры»**, а не готовым десятичным множителем
(`BASE_SCALE` в `BoardEntity`, `BEAM_SCALE`, `ELLIPSE_SCALE`, `PORTAL_SCALE` в `boosterFx`,
`restingScale` спецфишек, `FLIGHT_PROPELLER_SCALE` в `specialFx`,
`WAVE_SCALE` и `BALL_SCALE` в `boosterFx`). Числитель фиксирует, каким спрайт
обязан выглядеть; при перевыгрузке арта правится только знаменатель - в
скине. Знаменатель - не своя копия числа, а ширина текстуры из скина:
`skinTextureWidth(key)` отдаёт ширину файла, а без файла - холста. Поэтому
смена размера холста сама доходит до всех потребителей, а картинка другого
разрешения, заменившая холст, сохраняет размер на экране (ширину файла скин
указывает рядом с URL). Неизвестный ключ - исключение на импорте модуля, а не
`NaN` в масштабе.

Каждый раз, когда правило нарушали, ломалось одно и то же: перевыгрузка
текстуры молча меняла размер эффекта на экране (активный лазер съёживался до
10.8 дизайн-px, кольца луча вырастали с 78 до 155, луч ракеты переставал
перекрывать доску). Тот же принцип — для двух потребителей одной текстуры:
доска и панель целей (`GameGoalsPannel`) берут общий `BASE_SCALE`, а не каждый
своё число (иконка цели - `cellsSize / skinTextureWidth(текстура)`, у
предметов это ровно `BASE_SCALE`).

## Validation

После изменения флоу проверь:

- `npm run type-check`;
- `npm run lint`;
- `npm test` (перед выкладкой - `npm run test:ci`);
- `npm run build`, затем `npm run bundle:check`;
- визуально на mobile viewport: карточки `victory`/`defeat` не обрезают
  текст/кнопки; на десктопе партия стоит в колонке `--app-frame-width`, фон
  однотонный во всё окно;
- `?insets=47,34` на 375x667: шапка ниже верхнего отступа, «Цель» не касается
  доски, бустеры над нижним отступом;
- первый уровень идёт без панели бустеров, со второго (`?level=2`) панель на
  месте;
- победа (`?gameDebug=true`, «Выиграть») → карточка победы → «Дальше» →
  следующий уровень над бустерами; поражение → «Ещё раз» → тот же уровень;
- выход через кнопку в канвасе → сразу главная, **ни `victory`, ни `defeat` не
  показываются**; «Играть» продолжает с того же уровня;
- после перезагрузки «Играть» продолжает с открытого уровня: прогресс в
  `localStorage` (`match3-pixi:progress:v1`);
- то же на обоих рендерерах: `?renderer=webgl` и `?renderer=webgpu`
  (фактический - в отладочной панели `?gameDebug=true`); несколько выходов
  посреди эффекта и «Проиграть -> Ещё раз» - в DOM один канвас, в консоли нет
  ошибок и предупреждений Pixi («destroyed while still bound» и т.п.). Звук
  в такой проверке выключайте кнопкой на холсте.
